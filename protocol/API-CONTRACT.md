# Atermius API Contract v1

This contract aligns the Rust server, the Flutter client, and the black-box acceptance suite. `server/` must update this document whenever the implementation intentionally deviates; no endpoint is considered implemented just because it is listed here.

## Wire rules

- Base path: `/api/v1`; JSON is UTF-8. UUIDs are lowercase canonical strings. Potentially large sequence/cursor values (`device_seq`, `commit_seq`, `conflict_seq`, `resolution_seq`, history watermarks and `after_seq`) are decimal strings; bounded protocol/version/port/limit fields are JSON integers.
- Authenticated requests use `Authorization: Bearer <access-token>` outside browser cookie mode. Access tokens are short lived. Never put credentials or tickets in a URL.
- Every authenticated HTTP request also sends exactly one `X-Atermius-Capability-Marker` header with canonical value `v1` or `v2`. `v2` is a transport declaration that this current client can read schema-2 records, attachment manifest v2, and save attachments up to 1 GiB; it is not signed and never grants write eligibility. Missing, duplicate, malformed, or unknown values are treated as v1. The signed per-device capability report remains the sole v2 write gate. When a device next contacts the server with a missing/v1 marker, the server atomically removes that device's stored report only if it asserted the complete v2 capability. A marker cannot predict an offline rollback before that device contacts the server. If schema-2 data already exists, a v1 request that would read an envelope fails with `409 VAULT_CLIENT_CAPABILITY_REQUIRED`.
- The redaction-capability route requires exactly one canonical `X-Atermius-Redaction-Marker: v1` and rejects missing, duplicate, malformed, or unknown values. The signed report is only a device protocol-support claim: it does not prove clients received/applied redactions, authorize purge, or start permanent record purge.
- Browser clients use the same API origin by default. The current CORS allowlist includes `Authorization`, `Content-Type`, `X-Atermius-Capability-Marker`, `X-Atermius-Redaction-Marker`, `Range`, `If-Range`, and `X-Content-SHA256`; it exposes `ETag`, `Content-Range`, and `Accept-Ranges`. The redaction marker is independently required by its report route and is included in CORS preflight. Without `ATERMIUS_PUBLIC_ORIGIN`, cross-origin requests are disabled.
- API errors use `{ "error": { "code": "...", "message": "...", "request_id": "..." } }`. Error messages contain no submitted secret or database detail.
- Opaque identifiers are not authorization. Every resource lookup also checks current account, device and vault membership.
- The server stores and returns the exact client ciphertext. It never receives a vault key, master password, SSH private key or decrypted record.

## Instance and account

`GET /api/v1/instance` returns `{instance_id, server_space_id, generation, protocol_version, setup_required, restore_retention_days, capabilities, limits}`. `capabilities` describes server features only and includes `device_capability_reports`; it does not assert that any account device can read a record or attachment format. `terminal_collaboration` is present only when `ATERMIUS_TERMINAL_COLLABORATION_ENABLED=true` and `ATERMIUS_PUBLIC_ORIGIN` is configured. `restore_retention_days` is the configured tombstone restore deadline in days (default 30). `limits` is `{max_object_bytes,max_upload_chunk_bytes,max_record_object_refs}`: the configured per-object maximum (64 MiB by default), maximum bytes per chunk PUT (1 MiB), and maximum sorted references per signed revision (1024). `notifications` is present only when `ATERMIUS_PUBLIC_ORIGIN` is configured; the configured origin itself is not returned.

`POST /api/v1/auth/prelogin` request `{username}` returns `{account_id, kdf:{id,salt,mem_kib,iterations,parallelism,version}, auth_scheme}`. Unknown usernames receive a shape-compatible response; registration uniqueness is checked at commit.

`POST /api/v1/auth/register` creates the first account when setup is required, otherwise follows instance registration/invitation policy. The client generates the initial personal vault ID/key/name envelope and signs its first membership manifest; the server must not invent a vault key. Request:

```json
{
  "account_id": "client-generated-uuid",
  "username": "owner@example.test",
  "bootstrap_token": "one-time-secret-from-server-cli",
  "kdf": {"id":"argon2id13","salt":"base64url","mem_kib":65536,"iterations":3,"parallelism":1,"version":1},
  "login_verifier": "base64url-32-bytes",
  "account_key_envelope": {"version":1,"nonce":"base64url","ciphertext":"base64url"},
  "device": {"device_id":"uuid","name":"browser","signing_public_key":"base64url","encryption_public_key":"base64url","signature":"base64url"},
  "initial_vault": {
    "vault_id":"uuid",
    "name_envelope":{"version":1,"nonce":"base64url","ciphertext":"base64url"},
    "key_epoch":1,
    "membership_version":1,
    "key_envelope":{"recipient_device_id":"same-device-uuid","key_epoch":1,"membership_version":1,"envelope":{"version":1,"suite":"crypto_box_seal","ciphertext":"base64url"},"signature":"base64url"},
    "membership":{"membership_version":1,"previous_digest":null,"manifest":{"key_epoch":1,"display_name_envelope":{"version":1,"nonce":"base64url-24-bytes","ciphertext":"base64url"},"members":[{"user_id":"client-account-uuid","role":"owner","state":"active","encryption_key_fingerprint":"base64url-sha256"}],"signer_device_id":"same-device-uuid"},"signature":"base64url"}
  }
}
```

The client generates `account_id` before creating its signed initial membership manifest; the server validates UUID shape and uniqueness and adopts it only if the registration transaction succeeds. The verifier is a separately derived client login secret; it is not the master password or an encryption key. The account envelope is opaque ciphertext. `device.signature` is Ed25519 over UTF-8 JCS of `{account_id,device_id,signing_public_key,encryption_public_key}` and proves possession of the registered signing key. For `initial_vault.membership`, `signature` covers UTF-8 JCS of `{vault_id,membership_version,previous_digest,manifest}`. New clients must include `display_name_envelope` in that signed manifest, byte-for-byte equal as JSON to the top-level `initial_vault.name_envelope`; legacy signed manifests may omit the field and remain readable. The manifest also contains `key_epoch`, `members`, and `signer_device_id`. The sole initial member is the new Owner account, `signer_device_id` is the new device, both versions are 1, and `previous_digest` is null. For `initial_vault.key_envelope`, `signature` covers UTF-8 JCS of `{vault_id,recipient_device_id,key_epoch,membership_version,envelope}`; its recipient is the new device and its versions match the initial vault. The `envelope` value is opaque; clients use libsodium sealed boxes and validate all context after opening. Response returns `{account_id, access_token, expires_in, refresh_token, device_id, vaults:[...]}`. Account creation and initial device/personal-vault creation are atomic.

For subsequent accounts, omit `bootstrap_token` and provide `instance_invitation_token`. A local operator mints one with `atermius-server create-account-invite --username <email> [--expires-in-seconds N]` after the first account exists. The username is normalized by trimming whitespace and lowercasing; the default lifetime is seven days and accepted lifetimes are 60 seconds through 30 days. Reissuing for the same username revokes its earlier pending invitations. The token is one-use, bound to that normalized username, and its SHA-256 hash is stored instead of the bearer value. Successful account enrollment consumes the token in the same transaction as the account, first device, personal vault and session creation. It grants access only to the new account's personal vault. Team vault access still requires a separate owner-signed vault invitation and acceptance. Missing token returns `ACCOUNT_INVITATION_REQUIRED`; unknown, expired, replayed, revoked or username-mismatched tokens all return `ACCOUNT_INVITATION_INVALID`.

An allowlisted instance administrator can also manage these invitations in Settings. `GET /api/v1/admin/account-invitations?limit=50&offset=0` returns `{"invitations":[...],"total":N,"limit":50,"offset":0}`. Each row has exactly `invitation_id`, normalized `username`, `created_at`, `expires_at`, and `status`; status is one of `pending`, `expired`, `consumed`, or `revoked`. Rows are ordered by `created_at` descending then `invitation_id` descending. Page size is 1–100 and offset is 0–1,000,000. This endpoint never returns the token, token hash, or consumed user ID. Maintenance prunes terminal invitation rows after their terminal timestamp is older than `ATERMIUS_AUDIT_RETENTION_DAYS` (1–3650 days): `consumed_at`, `revoked_at`, or `expires_at` for an expired unconsumed/unrevoked invitation. Pending invitations and recent terminal rows remain. Each maintenance pass deletes at most four batches of 500 rows; invitation audit events are separate and follow the normal audit-retention path.

`POST /api/v1/admin/account-invitations` accepts exactly `{"username":"user@example.test","expires_in_seconds":604800}`; `expires_in_seconds` may be omitted to use the seven-day default and otherwise must be an integer from 60 through 2,592,000. It returns HTTP 201 with `{"invitation":{"invitation_id":"<uuid>","username":"user@example.test","created_at":"<RFC3339>","expires_at":"<RFC3339>","token":"<one-time bearer>"}}`. The bearer appears only in this creation response. The browser may display it for one copy operation and must clear it from in-memory UI state after copying or dismissing the confirmation; it is never reloaded from the server.

`POST /api/v1/admin/account-invitations/{invitation_id}/revoke` takes no body. Revoking a pending invitation and reissuing an invitation for the same username serialize with registration consumption in SQLite's writer transaction and, in restricted PostgreSQL mode, through the shared `instance_meta` row lock using PostgreSQL time. Repeated revocation of an already revoked invitation returns its revoked receipt; consumed or expired invitations return `409 ACCOUNT_INVITATION_NOT_PENDING`. Success returns exactly `{"invitation_id":"<uuid>","status":"revoked","revoked_at":"<RFC3339>"}`. These routes require a currently valid session/device and current instance-admin allowlist membership. Unauthenticated callers receive 401; authenticated non-admin callers receive 403. Issue and revoke actions are written atomically with their invitation state and instance audit event (`instance.account_invitation_issued` or `instance.account_invitation_revoked`), with the administrator user/device, HMAC resource ID, `source=api`, and no username or token in audit metadata. Reissue records revocation events for the superseded pending invitations before the new issue event. PostgreSQL revalidates the live administrator session, account, device and current allowlist inside the mutation transaction; token hashes are stored in the shared PG database and the one-time token is returned only in the issue response.

`POST /api/v1/auth/login` request `{username, login_verifier, device_id}`; success returns the same session fields as registration. `POST /api/v1/auth/refresh` takes `{refresh_token}` and atomically rotates both bearer values while preserving the session, account, and device identity. Its response is `{account_id,device_id,access_token,expires_in,refresh_token}`; the OpenAPI `RotatedSession` schema, Python integration assertions, and Flutter `AuthSession.fromJson` regression enforce these identity fields so clients can retain Vault descriptors while replacing session credentials. A refresh token is single-use. Reuse of a consumed token revokes every session in that family whose `revoked_at` is null and returns `401 AUTH_REQUIRED` when the revocation transaction commits; when at least one unrevoked family session row is actually revoked, the server best-effort writes one account-scoped `auth.refresh_reuse_detected` event in that transaction with null actor IDs, `resource_type: "session_family"`, and only the random family UUID as `resource_id`. The reused token, token hash, account/device IDs, IP, User-Agent, and request content are excluded. If the audit INSERT fails but the transaction commits, the revocation remains and the replay returns 401. If the transaction commit fails, the API returns `500 INTERNAL` and the revocation outcome is unknown. Repeated replay after revocation does not create another event. Unknown/expired tokens without a consumed-token history are not recorded. Permanent account purge clears the session-family resource ID. `POST /api/v1/auth/logout` revokes the current session.

`POST /api/v1/auth/password-change` requires the active bearer session and body `{operation_id,current_login_verifier,new_kdf,new_login_verifier,account_key_envelope}`. `operation_id` is a lowercase canonical UUID. `current_login_verifier` and `new_login_verifier` are client-derived 32-byte base64url-no-pad values; the master password is never sent. `new_kdf` has the exact registration KDF fields and bounds. `account_key_envelope` is the opaque rewrapped account-key envelope with exactly `version`, `nonce`, and `ciphertext`; it is validated as v1 ciphertext and the server never opens it. Every attempt is charged to the existing normalized-username+peer login limiter before Argon2 verification. A wrong proof returns generic `401 REAUTH_REQUIRED` and leaves credentials, envelope, version and sessions unchanged (apart from the limiter counter).

On success, one SQLite transaction checks the credential-version/hash snapshot, updates the server verifier hash, client KDF metadata and opaque envelope, increments `credential_version`, revokes all of the account's other sessions, stores the retry receipt and writes an `auth.password_changed` account audit event. The request's calling session/access token/refresh credential remains valid; no token or password material is returned. Response is `{status:"changed",operation_id,credential_version,session_preserved:true,other_sessions_revoked:true,already_applied:false}`. Other devices remain registered but must sign in again with the new verifier.

For response-loss recovery, the server retains one receipt for the most recent successful password change per calling session. It stores only the operation UUID, a server-keyed HMAC of the canonical request, the resulting credential version and time, never the request body or verifier/envelope values. Repeating that exact body with the same still-active session returns the same result with `already_applied:true`; changing the body while that receipt is current returns `409 IDEMPOTENCY_KEY_REUSED`. The receipt is replaced by the next successful password change in that session and is deleted with the session. Replaying a superseded request cannot change credentials because its old proof no longer verifies; the user can sign in with the new verifier. The route never retries or exposes master-password data.

### Optional TOTP MFA v1

Accounts without an active TOTP seed keep the existing `POST /api/v1/auth/login` response and session fields. With TOTP enabled, a correct password and active registered device return HTTP 202 with exactly `{mfa_required:true,challenge_id,expires_at,methods:["totp","recovery_code"]}` and issue no session/access/refresh credential. `challenge_id` is a random canonical UUID whose SHA-256 hash alone is stored. The five-minute challenge binds `user_id`, the requesting registered `device_id`, and `credential_version`; it is single-use, has at most five factor attempts, and at most five outstanding challenges per account. A credential change, device/account revocation, expiry, challenge replay, or invalid factor returns generic `401 AUTH_REQUIRED`. Login/MFA limiter denials return 429 with `Retry-After`; denied increments are committed. Successful factor verification, challenge consumption, replay-state/code consumption, session creation, and success audit share one SQLite writer transaction.

The only accepted `POST /api/v1/auth/login/mfa` bodies are `{challenge_id,totp_code}` or `{challenge_id,recovery_code}`. Exactly one factor is required. A successful response is the existing `AuthSession` DTO. TOTP follows RFC 6238 with HMAC-SHA-1, six digits, a 30-second step and a ±1 step clock-skew window. The current code step is atomically advanced for enrollment confirmation, login, recovery-code rotation and TOTP disable; a step already consumed by any of those operations is rejected. This prevents two concurrent challenges or settings actions from accepting the same TOTP step.

Enrollment and account settings require an active bearer session plus fresh `current_login_verifier`; the master password is never sent. `GET /auth/mfa` returns exactly `{enabled,recovery_codes_remaining}`. `POST /auth/mfa/totp/setup` returns `{secret,provisioning_uri,expires_at}` where `secret` is 20 random bytes encoded as uppercase RFC 4648 Base32 without padding (32 characters), and the pending setup expires after ten minutes. `POST /auth/mfa/totp/confirm` takes `{current_login_verifier,totp_code}` and returns `{recovery_codes:[...]}` exactly once after a valid, unused TOTP step. Ten unique recovery codes each contain 80 random bits, encoded as uppercase Base32 without padding and formatted `XXXX-XXXX-XXXX-XXXX`; the server stores an independent 16-byte random salt and HMAC-SHA-256 digest, never plaintext. Codes are normalized by removing hyphens and uppercasing for verification; each can be consumed once. `POST /auth/mfa/recovery-codes` replaces every previous code atomically after a fresh verifier and unused TOTP step. `DELETE /auth/mfa/totp` takes the same confirmation request and returns `{enabled:false,recovery_codes_remaining:0}` after deleting the seed, pending setup and recovery codes. MFA audit events include only fixed actions and account identifiers; they exclude factors, seed, codes, challenge IDs, tokens and request bodies.

The TOTP seed is encrypted at rest with XChaCha20-Poly1305 using a fresh 24-byte nonce and account-bound associated data. Its dedicated random 32-byte operator key is loaded from `ATERMIUS_MFA_ENCRYPTION_KEY_FILE`, a regular service-owner-only mode-0600 file. This key is separate from instance identity, authentication-limit and archive keys, is never written into SQLite or an instance backup, and is never derived from a user password/Vault key. A configured missing, symlinked, malformed, wrong-owner or overly permissive key prevents startup. If the setting is unset, the service can start; setup and TOTP verification return `503 MFA_KEY_UNAVAILABLE`. A password-verified login can still issue the normal challenge and an unused recovery code can complete it without decrypting the TOTP seed. Recovery-code rotation and TOTP disable also require the seed key and therefore remain unavailable until the original key is restored. Restore the exact key associated with an archived database before starting that restore. For an intentional key change, stop the server and use the offline `rotate-mfa-key` command described in [the TOTP seed-key rotation runbook](https://github.com/aterm-project/server/blob/main/docs/runbooks/mfa-seed-key-rotation.md); it atomically re-encrypts active and pending seed envelopes and leaves recovery-code hashes and replay state untouched. Retain old keys for backups encrypted before rotation. Permanent loss of the key matching the current database makes encrypted TOTP seeds unrecoverable; recovery codes preserve login only and do not recreate the seed.

Restoring an instance archive also invalidates MFA state from that database snapshot in the same transaction that rotates instance generation and revokes sessions: pending enrollments and login challenges are deleted, every archived unused MFA recovery code is consumed, active seeds remain enabled, and `last_totp_step` advances to at least the current 30-second step. One safe account event `auth.mfa_state_reset_by_restore` is recorded per enabled account without any factor or key material. After restoring the exact MFA key, wait for the next TOTP step to sign in, then rotate the recovery codes. If the key is unavailable, the archived MFA recovery codes were consumed by restore; use full account Recovery instead.

Successful signed full account Recovery clears active/pending TOTP seeds, every recovery-code row and outstanding MFA login challenge in the credential-rotation transaction. If TOTP was active, the same transaction writes the safe `auth.mfa_reset_by_recovery` event; the account must enroll a new seed. This uses the account-Recovery protocol and does not accept an MFA recovery code as proof of account cryptographic Recovery.

### Online account recovery v1 — routes and generation lifecycle implemented; full acceptance pending

This is the normative v1 wire contract. Recovery route handlers and client crypto/API/UI flows are present. Migration 0022's persistent monotonic generation lifecycle is exercised by the passing Python account-recovery flow: setup 0→1, rotation →2, full recovery →3, disable preserves 3, re-enable →4, and exact retries do not advance it. The focused Flutter Recovery suite passes 23/23, including full-flow crash/exact-retry and secure-store server-scoping coverage. The shared fixture `protocol/test-vectors/account-recovery-v1.json` is checked by production Dart crypto tests, independent Python/PyNaCl tests, and Rust descriptor/signature tests. The current Web bundle Recovery browser E2E passes setup, recovery-code copy/readback confirmation, rotation and persistence/network/server-storage scans. A Python fault injection also exercises a missing required source envelope and expects stale + rollback; the strengthened Relay/notification ticket-count snapshot assertions passed 1/1 (5.04s); the full Python suite now passes 62/62, including this fault injection and its rollback snapshot assertions. The current-bundle `WEB-RECOVERY-FULL-LOSS-01` now verifies the old device/session remains active before anonymous recovery (old bearer 200), Recovery revokes it after completion (old bearer 401), replacement-password login reads the preserved Host revision, and both browser profiles pass fail-closed storage scans with zero read failures. Deterministic SQLite purge/completion ordering tests pass 2/2. Migration 0023 and black-box checks now establish equal challenge-row count/write path across unknown, Recovery-disabled, inactive, configured-stale and configured-current starts; row owner values remain distinguishable and timing equivalence is unproven. Native-device recovery, remaining UI failure paths and independent crypto review remain pending. Dart analysis reports 0 errors, 2 unrelated existing warnings and additional infos.

Recovery code is exactly 32 CSPRNG bytes, shown as unpadded base64url; user-selected phrases are rejected. Let `ctx={account_id,instance_id,server_space_id,recovery_generation}`. Recovery envelope key derivation is `HKDF-SHA256(IKM=32-byte recovery code, salt=32 zero bytes, info=UTF8(JCS(["atermius","account-recovery-envelope",1,ctx])), L=32)`. The accountKey identity wrapper uses `HKDF-SHA256(IKM=32-byte random accountKey, salt=32 zero bytes, info=UTF8(JCS(["atermius","account-recovery-identity-wrap",1,ctx])), L=32)`. JCS means RFC 8785 canonical JSON. Rust/Dart implementations require shared known-answer vectors. Derived keys are memory-only. Recovery-code AEAD AAD is JCS `{format:"atermius-account-recovery-v1",account_id,instance_id,server_space_id,recovery_generation}`; accountKey identity AEAD AAD uses the same context with `format:"atermius-account-recovery-identity-v1"`. Do not add a `purpose` AAD field. Each envelope uses XChaCha20-Poly1305-IETF, a fresh 24-byte nonce, and exact wire shape `{version:1,suite:"xchacha20-poly1305-ietf",nonce,ciphertext}` with base64url-no-pad byte fields. Before encrypting the recovery-code envelope only, serialize the identity as canonical JCS UTF-8 JSON, append trailing ASCII space bytes (`0x20`) until the plaintext is exactly 512 bytes, and reject if canonical JSON exceeds 512 bytes. XChaCha20-Poly1305 adds a 16-byte tag, so decoded `recovery_envelope.ciphertext` is exactly 528 bytes. On decrypt, require 528 ciphertext bytes, remove only trailing ASCII spaces, and require valid canonical JSON. The accountKey identity wrapper is not padded.

The decrypted identity is strict canonical JSON with exact compact fields `{f,a,i,s,g,d,p,q,x,y}`: `f="atermius-recovery-identity-v1"`, `a/i/s/g` are account/instance/server-space/generation, `d` is the flat descriptor hash, `p/q` are the Ed25519 public key/seed, and `x/y` are the Curve25519 `crypto_box` public key/secret key, with key bytes base64url-no-pad encoded. It contains no Vault key, password/verifier, session token, device private key, SSH plaintext or record plaintext. The same Recovery identity is independently encrypted under recovery code and random `accountKey`. `accountKey` is not a Vault root/record key and does not derive Vault keys. Normal password change rewraps the existing accountKey and leaves Recovery code valid. Full recovery creates a fresh accountKey and fresh Recovery keypairs, increments generation, and replaces all Recovery envelopes/boxes.

The public descriptor is flat. Its hash is lowercase-hex SHA-256 of JCS exactly `{protocol:"atermius-account-recovery-descriptor-v1",account_id,instance_id,server_space_id,recovery_generation,recovery_public_signing_key,recovery_public_encryption_key}`. The client verifies that the public keys match the independently decrypted Recovery keypair and pins this hash. `recovery_identity_proof_signature` is the new Recovery Ed25519 signature over JCS `{protocol:"atermius-account-recovery-identity-v1",account_id,instance_id,server_space_id,recovery_generation,recovery_descriptor_hash,recovery_envelope_sha256,recovery_identity_envelope_sha256}`. Both envelope hashes are lowercase-hex SHA-256 over JCS bytes of the complete envelope JSON value. `previous_recovery_signature` is omitted on first setup; on rotation it is the old Recovery Ed25519 signature over JCS `{protocol:"atermius-account-recovery-rotate-v1",account_id,instance_id,server_space_id,old_recovery_generation,new_recovery_generation,old_recovery_descriptor_hash,new_recovery_descriptor_hash}`. The current registered device signs the exact configure request with `proof_signature`, covering every field except `proof_signature` itself, including both Recovery proofs; omitted fields remain omitted in the JCS input. During completion, the old Recovery signature authenticates the entire request and the new Recovery identity proof/transition still apply. Never silently accept or repin changed public keys/hash.

A Recovery key box is one immutable row per logical `(vault_id,key_epoch,recovery_generation)`, not per device or membership version. Plaintext is canonical JSON `{account_id,instance_id,server_space_id,vault_id,key_epoch,vault_key}` with a 32-byte Vault epoch key; ciphertext is libsodium `crypto_box_seal` to the current Recovery public encryption key. Its envelope is `{version:1,suite:"crypto_box_seal",ciphertext}`. `envelope_sha256` is lowercase-hex SHA-256 of decoded raw ciphertext bytes. Recovery Ed25519 signs JCS `{protocol:"atermius-account-recovery-v1",account_id,instance_id,server_space_id,recovery_generation,recovery_descriptor_hash,uploader_device_id,vault_id,key_epoch,envelope_sha256}`. The uploader ID must equal the active authenticated device, or the new device ID in full recovery. Server checks wire format, size, signature and authorization but cannot inspect sealed plaintext. Identical context/hash retry is idempotent; a different ciphertext for an already stored context in the same generation returns `409 RECOVERY_KEYBOX_CONFLICT`, and clients fetch existing state rather than overwrite it. A future generation replaces the previous set. After receiving a box, clients verify the Recovery signature before trying to decrypt it, then check all inner contexts and key length.

`required_contexts` are sorted distinct `(vault_id,key_epoch)` pairs for the account's active membership in active or deletion-grace Vaults: collect persisted Vault key-envelope rows for all account devices, including revoked devices, and add each Vault's active epoch. A finally purged Vault is excluded. Device enrollment/revocation alone does not change the set. For every target device envelope, select the highest stored valid `membership_version` for that Vault/epoch whose signed manifest exists, its chain verifies, `manifest.key_epoch` equals that epoch, the version is no greater than current, and the account is active in the current manifest. Target envelopes bind that selected version. If a required context lacks a readable source device envelope or eligible signed manifest, full recovery fails closed.

The server's valid Recovery statuses are `disabled|current|stale`. `current` means only that the server has at least one opaque Recovery box for every required context; it does not prove that any box decrypts or that its sealed key is valid. `stale` means one or more required contexts lack a box. Setup may upload any available subset and remain stale. Rotation must rebox every context already present in the old generation; it may add other contexts available to the current device, and the result can remain stale. Full completion must cover the full required set. A missing/unreadable source device envelope or invalid membership context is an error/fail-closed condition, not a fourth status. Authenticated `GET /contexts` returns stored box ciphertexts so a logged-in client can open/rebox historical contexts while rotating Recovery identity/code; it never returns a Vault key plaintext or Recovery private key. The anonymous `start` response reveals no Vault IDs, epochs, required-context list or key boxes.

#### Routes

All request bodies reject unknown fields. UUIDs are canonical lowercase. JCS signature inputs are UTF-8. Each recovery envelope/keybox is limited to 64 KiB; aggregate HTTP request size is limited to 1 MiB by the server body limit; required contexts are capped at 1000 (`409 RECOVERY_CONTEXT_LIMIT` when exceeded). Oversize requests return `413 PAYLOAD_TOO_LARGE`. `/api/v1/me` currently includes `recovery_status` from `disabled|current|stale`; Web setup/confirm/rotation and missing-source-row rollback have focused passing evidence, while timing privacy, native-device acceptance, remaining UI failure paths and independent crypto review remain pending; browser full-device-loss and both purge/completion transaction orders pass their current acceptance tests.

`PUT /api/v1/auth/recovery` enables or rotates a package and requires an active bearer session plus fresh login proof. Exact body:

```json
{
  "operation_id":"lowercase-uuid",
  "current_login_verifier":"base64url-32-bytes",
  "recovery_generation":1,
  "recovery_public_signing_key":"base64url-32-bytes",
  "recovery_public_encryption_key":"base64url-32-bytes",
  "recovery_envelope":{"version":1,"suite":"xchacha20-poly1305-ietf","nonce":"base64url-24-bytes","ciphertext":"base64url"},
  "recovery_identity_envelope":{"version":1,"suite":"xchacha20-poly1305-ietf","nonce":"base64url-24-bytes","ciphertext":"base64url"},
```

Prelogin, login and registration use persistent SQLite fixed-window limits keyed by normalized username, username+TCP-peer pair, and broad TCP peer IP. The values are HMACed with a random 32-byte secret in `ATERMIUS_DATA_DIR/auth-rate-limit.key`; usernames and addresses are not stored in the limiter table. The server does not trust `X-Forwarded-For` by default. Requests without ConnectInfo use an `unknown` peer bucket and still count against username limits. Defaults per 15-minute window are login 12/user, 8/pair, 3000/IP; prelogin 30/user, 20/pair, 6000/IP; registration 3/user, 3/pair, 60/IP. Override the window with `ATERMIUS_AUTH_RATE_WINDOW_SECONDS` (60..86400) and each threshold with `ATERMIUS_AUTH_{LOGIN|PRELOGIN|REGISTER}_{USER|PAIR|IP}_LIMIT`; invalid/out-of-range values use the defaults. The IP limits are intentionally broad for deployments where all browsers arrive through one reverse proxy. Username and pair buckets are checked first; requests rejected there do not consume the shared IP budget, preventing repeated attempts against one name from blocking other users behind a proxy. Requests that pass both narrower buckets consume the IP bucket, which bounds attempts across rotating usernames. The 100,000-row cap is global across auth operations and bucket scopes for the aligned active fixed window. When full, requests needing a new bucket fail closed with `RATE_LIMITED`; existing buckets continue to be counted. A structured `auth_rate_limit_capacity_exhausted` warning is emitted at most once per process per minute and contains only scope, endpoint and capacity, not a username or address. The aggregate metrics endpoint does not export per-attempt or per-username/IP limiter series. Each auth request first removes earlier-window rows in its transaction, so a rollover immediately frees capacity; hourly maintenance provides additional cleanup. A rejected request returns the same `{error:{code:"RATE_LIMITED",...}}` shape for known and unknown usernames, HTTP 429, and a `Retry-After` header containing seconds until the window resets. Registration attempts are charged immediately after username normalization, including unknown or invalid enrollment tokens, so token guessing is bounded; a throttled request does not consume a bootstrap/account-invitation credential. Expired limiter rows are removed by hourly maintenance.

Unknown prelogin usernames receive a deterministic, username-bound fake account UUID and KDF salt, derived with a separate HMAC domain from the private limiter key, so repeated prelogin calls have the same shape and stable decoy values without storing the submitted username. Unknown login usernames go through a dummy verifier using the same Argon2 parameters before returning the same `AUTH_REQUIRED` error as a wrong verifier.

Vault deletion reauthentication attempts are charged against the existing login rate-limit buckets before Argon2 verification, using the normalized account username and TCP peer. Failed and successful proofs count as attempts; a limited request returns `429 RATE_LIMITED` with `Retry-After` and skips verifier KDF work.

Only these fixed instance-wide gauges are emitted: `atermius_accounts{status="active|deleting|disabled"}`, `atermius_devices_active`, `atermius_vaults{state="active|deleting"}`, `atermius_blob_stored_bytes`, `atermius_upload_reserved_bytes`, `atermius_object_delete_queue{state="pending|retry_wait|quarantined"}`, `atermius_backup_last_success_timestamp_seconds`, `atermius_vault_quota_bytes`, and `atermius_ssh_relay_enabled` (0 or 1). `atermius_backup_last_success_timestamp_seconds` is the Unix timestamp of the last locally recorded successful encrypted archive creation; it is `0` when this data directory has no recorded local success. It does not prove off-host replication or restore verification. The best-effort private sidecar is not included in archives, so a restored data directory reports `0` until it creates a local backup. Object-delete values count durable queue rows by fixed state; they do not expose queue IDs, storage IDs, storage keys, Vault IDs, or user data. The only labels are the listed fixed lifecycle and queue-state values; the backup timestamp gauge has no labels. There are no account, device, Vault, hostname, request, or caller-controlled labels. The endpoint does not expose request latency, auth attempts, or per-user/per-Vault series. If the Bearer value does not match the active scrape verifier, normal account-session authentication and instance-admin allowlist checks apply; missing/invalid/expired/revoked sessions receive `401 AUTH_REQUIRED`, and authenticated callers outside the allowlist receive `403 INSTANCE_ADMIN_REQUIRED`.

`GET /api/v1/admin/metrics-credential` requires a current active account session and instance-admin allowlist. It returns exactly `{active,updated_at}`; `updated_at` is null when no credential is active and otherwise is the creation/last-rotation timestamp. It never returns a secret or verifier. `POST /api/v1/admin/metrics-credential` requires the same administrator session and an empty request body. It creates or rotates the single instance scrape credential and returns exactly `{credential,created_at}` once. The secret is `atm_` plus 32 random bytes encoded as unpadded base64url; rotation atomically replaces the prior verifier so the old value stops working immediately. Only an HMAC-SHA-256 verifier keyed with the server's private authentication-limit key is persisted. `DELETE /api/v1/admin/metrics-credential` requires the same administrator session, an empty body, and returns `{revoked:true}`; it is idempotent. POST and DELETE reject any non-empty body with `400 INVALID_REQUEST`. Successful create/rotate and effective revoke writes produce fixed instance-admin audit actions with the authenticated actor, `resource_type:"metrics_credential"`, and null resource ID; no secret, verifier, token fragment or request body is recorded. Missing/invalid/revoked administrator sessions receive `401 AUTH_REQUIRED`; authenticated callers outside the allowlist receive `403 INSTANCE_ADMIN_REQUIRED`. Install the one-time value directly into the scraper's protected secret configuration; never put it in a scrape URL or report body.

`GET /api/v1/admin/relay-policy` reads the durable administrator-selected Relay policy. `PUT /api/v1/admin/relay-policy` replaces it using optimistic concurrency and accepts exactly these fields (unknown fields are rejected):

```json
{
  "expected_revision": 0,
  "enabled": false,
  "allow_cidrs": [],
  "allow_ports": []
}
```

Both methods return the same bounded response shape:

```json
{
  "policy": {"enabled": false, "allow_cidrs": [], "allow_ports": []},
  "deployment_limits": {"relay_available": false, "allow_cidrs": [], "allow_ports": []},
  "max_connections_per_user": 4,
  "revision": 0,
  "updated_at": null
}
```

`policy` is the durable administrator selection; `deployment_limits` is derived only from server environment configuration and is read-only. A PUT must contain canonical network CIDRs (at most 256 entries, each at most 64 bytes), and each requested network must be wholly contained within a current deployment CIDR. Requested destination ports (at most 4096) must be unique and a subset of the deployment's exact-port list. Accepted lists are normalized into sorted order. The administrator can narrow these lists but cannot override deployment limits or the Relay target deny rules. If the operator later tightens the environment limits, GET continues returning the durable selection while effective authorization uses only its intersection with current limits; the administrator can then edit or clear the saved selection within those current bounds. `relay_available` is true only when the deployment enabled Relay and provides a configured public origin plus non-empty valid deployment CIDR and port lists. If false, the effective Relay service remains disabled even when a previously saved `policy.enabled` is true; restoring the deployment gate may make that saved selection effective again. The existing read-only admin overview reports the effective policy.

Without a persisted row, reads report revision 0, `updated_at: null`, and the current deployment Relay flag and allowlists as the default selection; this does not create a database row. A successful changed PUT increments the revision and records `admin.relay_policy_updated` with the authenticated administrator as actor in the instance audit log in the same transaction; it also invalidates all unused Relay tickets. An unchanged PUT is idempotent and does not increment the revision, change `updated_at`, write another audit event, or clear pending tickets. A stale `expected_revision` returns `409 RELAY_POLICY_CONFLICT` with no policy, audit, or ticket mutation. Malformed, duplicate, noncanonical, or out-of-range values return `400 INVALID_RELAY_POLICY_REQUEST`; enabling while the deployment gate is unavailable returns `422 RELAY_POLICY_UNAVAILABLE`; a CIDR/port outside deployment limits returns `422 RELAY_POLICY_OUTSIDE_LIMITS`. New ticket issuance uses the effective policy, and active Relay connections recheck it during their existing authorization polling and close when Relay is disabled or their destination is no longer allowed. A missing/invalid session returns `401 AUTH_REQUIRED`; an authenticated caller outside the current admin allowlist receives `403 INSTANCE_ADMIN_REQUIRED`.

`GET /api/v1/admin/relay-policy/users/{user_id}` reads the selected and effective Relay policy for an existing account; `PUT` changes that account's restriction and `DELETE` clears its override. All three require the caller's current active session and instance-admin allowlist. The target account is selected by the path UUID, while Relay ticket authorization always derives the user from its authenticated session. No row means the account inherits the current instance selection and follows later instance policy changes. A changed PUT accepts exactly `{expected_revision,expected_instance_policy_revision,enabled,allow_cidrs,allow_ports}` and can only narrow the current effective instance CIDR and exact-port sets; both revisions must be nonnegative integers. The server checks the submitted instance revision and account revision inside the same `BEGIN IMMEDIATE` write transaction before changing the override, revision watermark, audit ledger, or unused Relay tickets. A stale instance or account revision returns `409 RELAY_USER_POLICY_CONFLICT` with no side effects; clients must reload both policy snapshots before retrying. CIDRs and ports have the same 256/4096 bounds and canonical/unique requirements as the instance policy. The response contains `{user_id,inherited,policy,effective_policy,instance_policy_revision,revision,updated_at}`. A changed write records an HMAC-scoped `admin.relay_policy_updated` event and revokes that account's unused tickets in the same transaction. A DELETE accepts exactly `{expected_revision}`, removes the override row, increments a separate revision watermark, and restores inheritance; repeated reset and an unchanged PUT are no-ops. A stale revision returns `409 RELAY_USER_POLICY_CONFLICT`; malformed input returns `400 INVALID_RELAY_USER_POLICY_REQUEST`; a missing account returns `404 RELAY_USER_NOT_FOUND`; a setting outside the current instance policy returns `422 RELAY_USER_POLICY_OUTSIDE_LIMITS`, and enabling while the instance Relay gate is unavailable returns `422 RELAY_USER_POLICY_UNAVAILABLE`. Active connections recheck all effective policy scopes on the existing approximately two-second authorization poll and close when the effective policy disallows their fixed target. The server-managed Relay access-group semantics below also advance an authorization revision to close sockets on every group-membership or group-policy change, including changes that broaden the policy.

### Server-managed SSH Relay access groups

These administrative groups are server-owned access-control metadata. They are stored in dedicated tables, independent of encrypted, client-owned Vault workspace/group records. The server never treats client ciphertext as authoritative membership or ACL input. All group routes require a current active account/device session and the configured instance-admin allowlist.

`GET /api/v1/admin/relay-groups` returns `{groups:[...]}` summaries with `{group_id,name,revision,membership_revision,policy_revision,member_count,policy_inherited,updated_at}`. `POST` creates an empty group from exactly `{name}` and returns `201` with the same detail shape as `GET /api/v1/admin/relay-groups/{group_id}`. Names are trimmed and normalized with Unicode NFKC, contain 1–80 Unicode code points and at most 320 UTF-8 bytes, and reject control characters. Uniqueness is enforced by a stored key made from NFKC text, Unicode lowercase, and final NFKC normalization. This is lowercase normalization, not full Unicode case folding; e.g. compatibility forms normalized by NFKC share a key. A duplicate key returns `409 RELAY_GROUP_NAME_TAKEN`. The name revision begins at 1; membership and policy revisions begin at 0.

Group detail is `{group:{group_id,name,revision,created_at,updated_at},members:{revision,items:[{user_id,username}]},policy:{inherited,revision,updated_at,instance_policy_revision,policy,effective_policy}}`. Names have a 1–80 code point/320 UTF-8 byte boundary. Group identifiers and account identifiers are canonical UUIDs. The member list includes only the account UUID and normalized username for administrators; it contains no Vault or SSH record data. The three revision domains are independent: rename uses group `revision`, full-set membership replacement uses `members.revision`, and policy updates use `policy.revision` plus `instance_policy_revision`.

`PUT /api/v1/admin/relay-groups/{group_id}` accepts exactly `{expected_revision,name}` and renames the group. `DELETE` accepts exactly `{expected_revision,expected_membership_revision,expected_policy_revision}`, physically deletes it, cascades its memberships and policies, and returns `204` with an empty body. All three revision domains are checked atomically to prevent a stale detail view from deleting concurrent changes; conflicts return `409 RELAY_GROUP_CONFLICT`, `RELAY_GROUP_MEMBERSHIP_CONFLICT`, or `RELAY_GROUP_POLICY_CONFLICT` for the stale domain. Names are unique by the server's normalized name key. No-op rename is idempotent and does not audit or mutate revisions.

`PUT /api/v1/admin/relay-groups/{group_id}/members` accepts exactly `{expected_revision,user_ids}` and replaces the complete membership set. The list contains up to 1000 unique canonical account UUIDs. Newly added accounts must exist and be active; existing disabled accounts can remain unchanged or be removed. Duplicate/invalid/unknown/inactive-new IDs return `400 INVALID_RELAY_GROUP_MEMBERS_REQUEST`. A stale membership revision returns `409 RELAY_GROUP_MEMBERSHIP_CONFLICT`. A no-op replacement is idempotent. A changed set increments only the membership revision, advances a private Relay authorization revision for the union of old and new members, deletes their unused Relay tickets, and causes their existing Relay connections to close at the next authorization poll (no later than about two seconds, subject to the bounded database check). This forced close applies even if removing a restriction makes a fresh connection permissible.

`GET /api/v1/admin/relay-groups/{group_id}/relay-policy` reports the group's policy snapshot. A missing override means `inherited:true`, revision 0 before any reset, and selection from the current instance policy. `PUT` accepts exactly `{expected_revision,expected_instance_policy_revision,enabled,allow_cidrs,allow_ports}`; both revisions must match inside one write transaction. CIDR and exact-port validation follows the instance/user Relay bounds and canonical requirements. A group override must be contained by the current effective instance CIDR and port limits; group overrides cannot widen those limits. Stale group or instance revisions return `409 RELAY_GROUP_POLICY_CONFLICT`; malformed input returns `400 INVALID_RELAY_GROUP_POLICY_REQUEST`; a value outside current limits returns `422 RELAY_GROUP_POLICY_OUTSIDE_LIMITS`; enabling while the instance gate is unavailable returns `422 RELAY_GROUP_POLICY_UNAVAILABLE`. Changed policy writes increment the policy revision, record an HMAC-scoped admin audit event with no group name or members, bump current members' authorization revisions, and revoke their unused tickets. An unchanged PUT does none of those.

`DELETE /api/v1/admin/relay-groups/{group_id}/relay-policy` accepts exactly `{expected_revision}`, removes the override, increments the policy watermark, restores inheritance, and returns full group detail. The watermark remains after reset, so stale writes cannot pass through an override-delete cycle. Reset while already inherited is idempotent. Changed reset audits the action, invalidates current member tickets, and closes their active Relay sockets on recheck.

The effective Relay policy is the intersection of deployment limits, instance policy, the optional per-user administrator restriction, and every explicit group policy assigned to that user; the enabled flags combine with logical AND. An inherited group contributes the current instance policy. Group-policy state is loaded from server-controlled tables on ticket issuance, ticket redemption, before TCP connection accounting, and each active connection authorization poll. The one-use ticket stores a private per-user authorization revision. Membership changes and group-policy set/reset/delete advance that revision for affected users and revoke unused tickets atomically; Relay sockets bound to older revisions are closed even where the new selection still allows their target. Group name edits do not affect access or authorization revisions. Audit actions are fixed strings; group resource identifiers are HMAC-scoped by the instance audit pipeline, and member lists, names, and policy values are not copied into audit event fields.

`GET /api/v1/admin/backup-status` uses the same current-session, account/device and instance-admin allowlist checks in one read transaction. It returns the latest `backup` attempt recorded in this data directory, whether started by the operator CLI, the allowlisted admin job, or the durable scheduler; `verify-backup` never changes the status. A missing sidecar is represented by `last_attempt: null`. The endpoint deliberately does not claim that an archive moved off-host still exists or is restorable.

```json
{
  "operation": "backup",
  "last_attempt": {
    "attempted_at": "2026-09-30T12:00:00.000Z",
    "result": "succeeded",
    "migration_version": 23,
    "archive_bytes": 1048576,
    "failure_category": null
  }
}
```

`result` is `succeeded` or `failed`. On failure, `migration_version` and `archive_bytes` are null and the only `failure_category` is the fixed value `backup_failed`; error text is not persisted or returned. Success records the archive's migration version and encrypted byte length. The mode-0600 `backup-status.json` sidecar is atomically replaced inside the mode-0700 instance data directory and is not included in instance archives, so a restored data directory starts without this best-effort sidecar value. The durable schedule configuration and run rows are stored in SQLite and are included in the encrypted archive. The API and sidecar never store archive/key paths or key bytes; schedule interval is reported only by the separate schedule endpoint.

`GET /api/v1/admin/backup-replication` requires the same current session,
device and instance-admin allowlist validation. Its exact response envelope is
`operation: "backup_replication"`, `configured`, `pending_count`, and nullable
`latest_attempt`. The latest attempt contains only `archive_id`, fixed `state`,
`attempted_at`, nullable `completed_at`, nullable `archive_bytes`, and nullable
`failure_category`. `pending_count` includes `pending_archive`, `pending`,
`running`, `retry_wait`, and `interrupted`, but excludes terminal `failed` and
`succeeded` rows. Failure categories are the fixed values
`archive_unavailable`, `credentials_invalid`, `remote_unavailable`,
`remote_integrity_mismatch`, and `replication_failed`. The endpoint never
returns endpoint, bucket, prefix, object key, credential path/content, provider
error text, or a filesystem path.

Replication is configured only by server environment values:
`ATERMIUS_BACKUP_S3_BUCKET`, `ATERMIUS_BACKUP_S3_REGION`, and
`ATERMIUS_BACKUP_S3_CREDENTIALS_FILE` are all required when any S3 replication
setting is supplied. Optional values are `ATERMIUS_BACKUP_S3_ENDPOINT_URL` and
`ATERMIUS_BACKUP_S3_PREFIX`. An unset configuration disables replication;
partial or explicitly empty configuration fails closed. The credential file
is a private owner-only regular JSON file outside the instance data and local
archive directories, with exactly `access_key_id`, `secret_access_key`, and
optional nullable `session_token` fields. The server uses this static provider
explicitly and never accepts target details through an administrator API.

The outbox row is inserted before a generated archive snapshot and carries the
archive UUID, origin, size/hash, attempts, retry/status timestamps and any
multipart upload ID. All retries and restart reconciliation use the same key:
`<prefix>/atermius/v1/<instance-id>/<archive-id>.atb`. Only completed encrypted
archive bytes are sent to object storage. Put and multipart completion use
`If-None-Match: *`; 412/409 conflicts trigger HEAD plus a full GET digest and
encrypted-archive authentication check. Identical valid bytes are idempotent
success; mismatched bytes are a terminal integrity failure and are not
overwritten. Provider failures are reduced to the fixed categories above.
Retryable attempts use bounded exponential backoff. Running and unsuccessful
rows protect local archives from local retention; failed rows do not count as
waiting, but remain protected until operator investigation. The server never
deletes completed remote objects. Providers must support object HEAD/GET,
SHA-256 checksum and metadata, conditional Put/Complete, multipart
create/upload/complete/abort, and paginated `ListMultipartUploads`. Configure a
provider lifecycle rule to abort incomplete multipart uploads after one day
for the narrow crash window before an upload ID can be persisted.

`GET /api/v1/admin/backup-schedule` returns the durable schedule and the latest scheduled occurrence. `PUT /api/v1/admin/backup-schedule` accepts exactly `{"interval_hours": N}` for an integer `N` from 1 through 720, or `{"interval_hours":null}` to disable scheduling. Both methods require an active session and the current instance-admin allowlist. The PUT response is the same DTO as GET; malformed bodies return `400 INVALID_BACKUP_SCHEDULE_REQUEST`, out-of-range values return `400 INVALID_BACKUP_INTERVAL`, and enabling without valid private archive/key settings returns `503 BACKUP_NOT_CONFIGURED`.

```json
{
  "operation": "backup_schedule",
  "backup_configured": true,
  "interval_hours": 24,
  "next_run_at": "2026-10-03T12:00:00Z",
  "last_run": {
    "run_id": "lowercase-canonical-uuid",
    "scheduled_for": "2026-10-02T12:00:00Z",
    "started_at": "2026-10-02T12:00:00Z",
    "finished_at": "2026-10-02T12:00:03Z",
    "status": "succeeded",
    "result_code": "completed",
    "archive_bytes": 1048576,
```

`backup_configured` reports only whether the private archive/key settings currently validate; it does not expose their paths or contents. A non-null `interval_hours` enables the schedule. `next_run_at` is null while disabled. `last_run` is null until a scheduled occurrence is claimed; subsequent records expose only the generated opaque run ID, due/start/finish timestamps, fixed status/result, and archive size/schema version. Schedule changes serialize with maintenance and backups under the shared operation lock and emit the instance audit event `admin.backup_schedule_updated` attributed to the authenticated administrator. Each due occurrence and the next due time are committed together before archive creation. If the server stops during a run, startup marks that occurrence interrupted and does not replay it; the next occurrence remains scheduled for the next interval. Scheduled run IDs join manual server-backup job IDs in bounded local retention. No archive/key paths, key bytes, error strings, or client data are returned.

The per-Vault quota routes are implemented and covered by server/API acceptance tests. `GET /api/v1/admin/vaults?limit=50&offset=0` lists existing Vaults, including Vaults in deletion grace, and returns the total number of rows before pagination:

```json
{
  "vaults": [{
    "vault_id": "lowercase-canonical-uuid",
    "owner_user_id": "lowercase-canonical-uuid",
    "owner_username": "owner@example.com",
    "state": "active",
    "stored_bytes": 0,
    "reserved_upload_bytes": 0,
    "quota_bytes": 1073741824,
    "created_at": "2026-09-29T12:00:00Z"
  }],
  "total": 1,
  "limit": 50,
  "offset": 0
}
```

`limit` defaults to 50 and accepts 1 through 100; `offset` defaults to 0 and accepts 0 through 1,000,000. Malformed or out-of-range pagination returns HTTP 400. `vault_id` and `owner_user_id` are canonical lowercase UUIDs; `owner_username` is the normalized account username; `state` is `active` or `deleting`; `created_at` is UTC RFC3339. `stored_bytes` is the total size in bytes of completed blob payloads in that Vault, and `reserved_upload_bytes` is the total expected size of unexpired uploads in that Vault. SQLite counts open reservations; restricted PostgreSQL counts both `open` and `completing` reservations using database time. The PostgreSQL list uses a repeatable-read snapshot. These fields exclude all client content and are computed from server-side object metadata. The route requires the current active session, device, account and instance-admin allowlist membership.

`PUT /api/v1/admin/vaults/{vault_id}/quota` changes a Vault's quota. `vault_id` must be a canonical lowercase UUID. The request body is exactly `{"quota_bytes":<integer>}`; the value must be at least 1 byte and no greater than 1 TiB (`1099511627776` bytes). Zero returns HTTP 400 `INVALID_QUOTA`; other malformed quota values or a malformed UUID also return HTTP 400. Success returns `{vault_id,quota_bytes,stored_bytes,reserved_upload_bytes,updated_at}`, where the usage fields report completed blob bytes and unexpired reservation bytes. Used bytes are `stored_bytes + reserved_upload_bytes`. In restricted PostgreSQL mode this includes both `open` and `completing` uploads, calculated against PostgreSQL time. An unknown Vault returns 404; a Vault that is not active, or a quota below current used bytes, returns 409. A PG write revalidates the current session/account/device/admin allowlist in the transaction and locks the Vault row used by upload initialization/completion before checking usage. This serializes reservation creation and quota reduction so the resulting quota never falls below committed usage. The quota update and instance-scope audit event commit atomically; the event records the authenticated actor's user/device identifiers and an HMACed Vault resource identifier, never the raw Vault ID.

Account and session controls are available only to the current authenticated instance-admin allowlist. `GET /api/v1/admin/accounts?limit=50&offset=0` returns a bounded account page containing `user_id`, normalized `username`, status (`active`, `disabled`, or `deleting`), creation time, and active device/session counts. It never returns password verifiers, account-key envelopes, device public keys, session token hashes, Vault IDs, or client data. `GET /api/v1/admin/accounts/{user_id}/sessions?limit=50&offset=0` returns session/device IDs and names, timestamps, revocation time, and an effective `active` flag; token hashes, source addresses, and payloads are excluded. Account and session pagination defaults to 50 rows, accepts 1–100, and caps offset at 1,000,000.

The restricted PostgreSQL runtime supports the Vault quota routes above, the two account/session GET projections, the exact account-status and session-revoke routes below, and account invitation list/issue/revoke. Reads use repeatable-read transactions that revalidate the current session, account, device and configured administrator allowlist before returning a page; data changes are shared across PG nodes. Quota writes lock the target Vault row used by upload reservation/completion. Account-status and session-revoke writes lock the target account lifecycle and its sessions. Invitation writes serialize through the shared `instance_meta` row used by registration. Every write revalidates the actor and commits the change with its audit record. Other unsupported admin routes remain blocked by the exact route allowlist and return `503 PG_SYNC_SCOPE_LIMITED`; SQLite continues to support the complete control set described below.

`PUT /api/v1/admin/accounts/{user_id}/status` accepts exactly `{"status":"disabled"}` or `{"status":"active"}`. Disabling atomically changes an active account to `disabled` and revokes every unrevoked session. It leaves devices, Vault membership, encrypted data, and deletion state untouched. Enabling changes `disabled` to `active` but does not restore old sessions; the user must log in again. Same-status requests are idempotent and do not create a transition event. The current administrator cannot target their own account or sessions, a `deleting` account cannot be changed, and the last active allowlisted administrator cannot be disabled. `POST /api/v1/admin/accounts/{user_id}/sessions/revoke` revokes all sessions without disabling an active account; `POST /api/v1/admin/accounts/{user_id}/sessions/{session_id}/revoke` revokes one session that belongs to the selected account. Repeated session revocation is a safe no-op. Successful changes are audited in instance scope with actor IDs and an HMACed account resource ID in the same transaction. PG writes acquire a shared account-admin serialization fence, then the same per-account lifecycle advisory lock used by login and refresh before locking session rows and the account. This makes status/session changes atomic across nodes: if login or refresh commits first, a later disable revokes its session; if disable commits first, login and refresh cannot produce usable credentials. Re-enabling requires a new login.

Disabling prevents new server authentication and revokes sessions, but does not erase encrypted data already cached on a device or affect SSH connections opened directly by a client. Existing server Relay and notification connections recheck session state on a roughly two-second interval and close after a failed check; an already-authorized request may finish before the next check.

`GET /api/v1/admin/audit?limit=100&cursor=<opaque>` pages instance-scope audit events for the current authenticated, allowlisted administrator. The endpoint is implemented and accepted with Rust authorization/cursor tests, disposable-server HTTP integration coverage, and an admin-only Flutter Settings panel. The response is:

```json
{
  "events": [{
    "event_id": "123",
    "scope": "instance",
    "actor_user_id": "account-uuid-or-null",
    "actor_device_id": "device-uuid-or-null",
    "action": "action-label",
    "resource_type": "resource-type",
    "resource_id": "hmac-or-null",
    "result": "success",
    "occurred_at": "2026-09-29T12:00:00Z",
    "source": "api"
  }],
  "next_cursor": "opaque-or-null",
  "has_more": false
}
```

`limit` defaults to 100 and must be in `[1,200]`; invalid values return `400 INVALID_LIMIT`. Omit `cursor` for the first page. The opaque HMAC-authenticated cursor is bound to the requesting admin account, instance generation, fixed high-water mark, and last event ID; it cannot be transferred to another administrator. Events committed after the initial high-water mark are excluded from that traversal. `next_cursor` is null when the traversal is complete. A malformed, modified, or wrongly bound cursor returns `400 INVALID_AUDIT_CURSOR`; a cursor from a prior instance generation returns `410 AUDIT_CURSOR_EXPIRED`, and the client restarts pagination without a cursor.

This route selects only `scope_type='instance'`; it does not expose the separate account- or Vault-scope audit feeds. Event actor IDs are returned only when present; a purged actor may have null IDs. `resource_id` is the stored keyed HMAC identifier, never a raw Vault ID. The page contains no Vault names, account usernames, source addresses, request bodies, ciphertext, credentials, SSH data, or other client payloads. The same active-session and current allowlist checks apply on every page.

`GET /api/v1/admin/restore-sources?limit=50&offset=0` lists bounded safe metadata for available server-generated encrypted archive candidates. Pagination defaults to 50 rows, accepts 1–100, and caps the offset at 1,000,000. The response is `{"sources":[...],"total":N}` in newest-first order. Each source contains a canonical `archive_id` UUID, `created_at`, positive `archive_bytes`, fixed `origin` (`manual` or `scheduled`), and fixed `source` (`local` or `replica`). Rows are unique by `(archive_id,source)`; the same archive may have one row per source. Ordering is `created_at` descending, `archive_id` descending, then local before replica. The ID is the durable backup job or scheduled-run ID. The route does not list CLI-created archives and never returns a path, basename, key, or internal error. Missing or invalid private archive/key configuration returns `503 BACKUP_NOT_CONFIGURED`; the restore worker revalidates local files or rechecks and authenticates the replica object after it acquires the shared maintenance lock. A restored database may show its archive row as interrupted because an archive snapshot is taken before its backup job reaches a terminal state.

`GET /api/v1/admin/jobs?limit=50&offset=0` lists persisted instance-admin job metadata. Pagination defaults to 50 rows, accepts 1–100, and caps the offset at 1,000,000. It returns `{"jobs":[...],"total":N,"supported_actions":[...]}` in newest-first request order. `supported_actions` describes the backend's available actions: the SQLite runtime returns `maintenance`, `backup`, and `restore`; the restricted PostgreSQL runtime returns only `maintenance`. Each row contains only `job_id`, `request_id`, `action`, nullable `archive_id`, nullable `archive_source`, `status`, `requested_at`, `started_at`, `finished_at`, and `result_code`; `archive_source` is null for maintenance and backup jobs and is local or replica for restore jobs. The response omits requester identity and internal maintenance details. For restore, `job_id` is also the safe stage ID used by the operator runbook.

`POST /api/v1/admin/jobs` accepts exactly `{"request_id":"<canonical lowercase UUID>","action":"maintenance"}`, `{"request_id":"<canonical lowercase UUID>","action":"backup"}`, or `{"request_id":"<canonical lowercase UUID>","action":"restore","archive_id":"<canonical lowercase UUID>","archive_source":"local|replica"}` and returns HTTP 202 with `{"job":<row>}`. Unknown fields, noncanonical IDs, a missing restore `archive_id` or `archive_source`, an `archive_id` or `archive_source` on another action, and unsupported actions are rejected. In restricted PostgreSQL mode, only `maintenance` is accepted; `backup` and `restore` return 503 `PG_ADMIN_ACTION_UNSUPPORTED` because archive execution is bound to the SQLite database. `request_id` is globally unique: replay by the same administrator/device returns the same job row only for the same action and payload, while reuse with another requester or payload returns 409 `JOB_REQUEST_ID_CONFLICT`. PostgreSQL replay binds the key to both the administrator and device. At most one job across all supported actions may be queued or running; another distinct request returns 409 `MAINTENANCE_ALREADY_RUNNING`. Local candidates are revalidated before acceptance. Replica acceptance checks that the archive has a successful local outbox record and replication is configured; it does not make a remote network request in the API handler. The worker rechecks the exact remote object under the maintenance lock, so an object removed or changed around submission can cause the accepted job to finish with the fixed `restore_failed` result. The response and job metadata do not expose remote failure details.

The fixed `backup` action is available only when the server is configured with both `ATERMIUS_BACKUP_ARCHIVE_DIR` and `ATERMIUS_BACKUP_KEY_FILE`. These settings are optional at server startup so existing deployments continue to boot. The archive directory must already exist as a service-owned mode-0700 directory outside `ATERMIUS_DATA_DIR`; the key path must name a service-owner-only regular file containing exactly 32 raw key bytes outside `ATERMIUS_DATA_DIR`. Missing or invalid settings cause `503 BACKUP_NOT_CONFIGURED` before a job is accepted. The worker repeats validation after acquiring the shared maintenance/backup interprocess lock. If settings become invalid after acceptance, the durable job fails with the fixed `backup_failed` result code and the backup-status sidecar records a generic failure.

For `backup`, the server creates the encrypted archive under the configured directory using a generated timestamp/UUID basename. The path and basename are not returned or persisted in the job row, audit event, or backup-status sidecar. Requests cannot supply filesystem paths or key material. Archive creation is the success boundary: updating `backup-status` is best effort afterward, so a sidecar write failure does not cause an already-created archive to be reported as failed or retried. Optional local retention keeps only a configured count of eligible server-created archives during maintenance; it does not manage operator CLI archives or off-host storage. The backup job uses the same interprocess lock as maintenance and the explicit-path backup CLI.

For `restore`, `archive_id` must refer to an available server-generated archive candidate from the restore-source catalog. The worker revalidates the archive’s generated name, ownership, permissions and file type under the shared maintenance lock, then verifies and restores it into a new private `restore-staging/atermius-restore-<job_id>` directory beneath the configured archive directory. The active `ATERMIUS_DATA_DIR` is never replaced. The live database receives the durable restore-job state and corresponding admin-audit events; account, Vault, session, and generation data are not changed. Runtime-policy drift fails closed; this online action has no drift-acceptance option. Atomic no-replace publication currently requires a Linux server; other server OSes fail the job without changing live data. On restart, missing/unavailable optional backup configuration or an invalid stage receipt/database/key marks the restore job interrupted, leaves stage paths untouched, and does not prevent the live service from starting. The UI prepares only an isolated copy. It does not stop the service, change an environment variable or Compose volume, activate the stage, or restart the service. Operators must follow the offline cutover and post-restore checks in the runbook while preserving the old data directory for rollback. The stage target is never returned by the API; it is derived locally from the configured archive directory and safe stage/job ID. Result codes are `completed`, `maintenance_failed`, `backup_failed`, `restore_failed`, and `interrupted`.

Job states are `queued`, `running`, `succeeded`, `failed`, or `interrupted`. Result codes are restricted to `completed`, `maintenance_failed`, `backup_failed`, `restore_failed`, and `interrupted`. A succeeded row has `result_code="completed"`; failed rows use the action-specific fixed failure code; a job left queued or running when the server restarts is reconciled to a fixed terminal state before serving. The queued/running/succeeded/failed/interrupted transitions and timestamps are persisted in SQLite. The server serializes the admin-triggered operation with its normal hourly and CLI maintenance pass. Callers cannot supply commands, paths, SQL, target directories, or cleanup parameters.

Request, start, completion/failure, and restart interruption are written to the instance-scope audit feed. Events retain the actor user/device IDs and use an HMAC resource identifier for the job. Maintenance events use `admin.maintenance_*`; backup events use `admin.backup_requested`, `admin.backup_started`, `admin.backup_completed`, `admin.backup_failed`, or `admin.backup_interrupted`; restore events use `admin.restore_requested`, `admin.restore_started`, `admin.restore_completed`, `admin.restore_failed`, or `admin.restore_interrupted`. Schedule mutations emit `admin.backup_schedule_updated` and always retain the real authenticated administrator/device actor; scheduled execution rows do not invent a human actor. `result` is `success` for requests, starts, and completed jobs, and `failure` for failed or interrupted jobs. Failures exposed to clients contain only the safe result code; internal errors are not returned. Restore staging uses a durable receipt so restart recovery can distinguish a fully published isolated target from an incomplete run without replaying it.

## Devices, vaults and membership

Vault presence is a short-lived lease, separate from encrypted records, record history, and audit events. `POST /api/v1/vaults/{id}/presence` accepts no request body and derives user, device, session, and bearer-token hash only from the authenticated request. It returns `{expires_at,ttl_seconds:90}`. A caller-supplied principal/payload returns `400 PRESENCE_BODY_NOT_ALLOWED`. Clients renew every 30 seconds while a Vault workspace is active; a lease expires after 90 seconds and expired leases are never returned. Storage is session-scoped so independent profile/session leases do not overwrite each other. A persistent rate gate keyed by `(vault_id,session_id)` permits at most one heartbeat every 5 seconds per pair, so switching to another authorized Vault is not blocked. A faster repeat returns fixed `429 PRESENCE_HEARTBEAT_RATE_LIMITED` with `Retry-After: 5` and does not extend the lease; a Members-panel GET can still refresh the online list. `GET /api/v1/vaults/{id}/presence` returns `{devices:[{user_id,device_id,last_seen_at}],ttl_seconds:90}` and does not echo the Vault ID. Concurrent live sessions for one device collapse to one entry, using the latest heartbeat. Only active member accounts, devices, sessions, and leases are listed. Both endpoints revalidate the authenticated session/device and active Vault membership on every request; heartbeat checks and upserts in one writer transaction, while list checks and reads in one read snapshot. A missing/nonmember Vault returns the same generic 404. Expiration is hard-filtered during list and capacity checks. Startup/hourly maintenance and the operator maintenance command physically remove expired or revoked leases and stale heartbeat-gate rows; heartbeats do not sweep the table. The writer transaction permits at most 8 live session leases per user/Vault and 100,000 per instance. A new lease over either bound returns the fixed `409 PRESENCE_LEASE_LIMIT`; renewing an already-live lease remains allowed. The DTO contains no device name, Host, terminal, content, IP, token, or audit fields.

- `GET /api/v1/me` returns account identity, current device and policy plus the caller's opaque `account_key_envelope`, `account_key_envelope_version` (integer, starting at 1), and current server-computed `recovery_status` from `disabled|current|stale`. This profile route never returns the recovery-code envelope or Recovery public/private keys; authenticated Recovery descriptor and opaque boxes come from `/api/v1/auth/recovery/contexts`. `policy.instance_admin` is a boolean reflecting whether the account's normalized username is in the configured instance-admin allowlist. This flag is informational; admin endpoints independently require the current active authenticated session and current allowlist membership. The account-key envelope is scoped to that authenticated account and must never be exposed in public instance/prelogin responses.
- `GET /api/v1/devices` lists the caller's devices as `{devices:[{device_id,user_id,name,signing_public_key,encryption_public_key,status,created_at,revoked_at,capability_report}]}`. Every listed device has the caller's `user_id`; clients use it to bind local approval certificates to the logged-in account. `capability_report` is null if no report was submitted. An absent report is treated as the legacy capability `{max_record_schema:1,host_attachment_manifest_versions:[1],max_attachment_bytes:268435456}`. `POST /api/v1/devices` registers a device through approval by the caller's currently authenticated device. This v1 flow supports manual/QR transfer of the new device's public enrollment request; it does not claim password-only enrollment without an existing trusted device. Request:
```json
{
  "device": {"device_id":"new-device-uuid","name":"laptop","signing_public_key":"base64url","encryption_public_key":"base64url","signature":"base64url"},
  "approver_device_id":"current-device-uuid",
  "certificate_signature":"base64url",
  "vault_key_envelopes":[
    {"vault_id":"vault-uuid","recipient_device_id":"new-device-uuid","key_epoch":1,"membership_version":1,"envelope":{"version":1,"suite":"crypto_box_seal","ciphertext":"base64url"},"signature":"base64url"}
  ],
  "capability_report": {"account_id":"account-uuid","device_id":"new-device-uuid","revision":1,"max_record_schema":2,"host_attachment_manifest_versions":[1,2],"max_attachment_bytes":1073741824,"signature":"base64url-ed25519"}
}
```

The new device's `device.signature` is its self-proof: Ed25519 over UTF-8 JCS of `{account_id,device_id,signing_public_key,encryption_public_key}`. The authenticated approver device must equal `approver_device_id`; its Ed25519 `certificate_signature` covers UTF-8 JCS of `{account_id,approver_device_id,device}` including the self-proof. Each key-envelope signature covers UTF-8 JCS of `{vault_id,recipient_device_id,key_epoch,membership_version,envelope}` and is verified with the approver device's registered signing key. An optional candidate-device `capability_report` uses the signature format below and is independently verified using the candidate signing key. In one transaction, the server checks each target and envelope context, checks that the approver currently has access to the vault and the referenced epoch, requires the submitted `(vault_id,key_epoch,membership_version)` set to match the approver device's currently stored key-envelope set, checks any required record-schema floor, registers the device, and stores the exact opaque envelopes/report. Registration into an active schema-2 vault returns `409 DEVICE_CAPABILITY_REQUIRED` unless that report advertises schema 2, attachment manifest v2, and at least 1073741824 attachment bytes. The recipient is the new device. This lets the same account recover every vault and historical key epoch already available to the approving device; it does not expose plaintext keys to the server. If the account has no active Vault memberships, the valid set is empty: the approval certificate still authorizes device enrollment, and the request must contain `"vault_key_envelopes":[]`. A non-empty set remains invalid when the server's current set is empty. A user may have at most 20 active registered devices; revoked devices do not count. `POST /api/v1/devices` checks the limit in the same SQLite writer transaction as enrollment and returns `409 ACTIVE_DEVICE_LIMIT_REACHED` at capacity without committing a candidate device, key envelope, or capability report. Full-loss Recovery revokes the previous active set and registers the replacement atomically; any later failure rolls the transaction back. The new device may log in only after registration succeeds. `GET /api/v1/vaults` may return an empty `vaults` array for a valid authenticated account. Login remains account-scoped; clients present an account workspace with device and account controls, but do not construct a Vault repository or run Vault sync until access returns or a new Vault is created. Existing encrypted local rows and pending operations stay scoped to their original Vault IDs. The approval response is an enrollment-time snapshot: while the target is offline, later rotations or newly shared Vaults can add server envelopes. Clients verify every current server envelope against the signed membership chain and may accept that authenticated current set even when it is a superset of the approval snapshot; any still-visible envelope with the same `(vault_id,key_epoch,membership_version)` as the approval must match exactly. Signed approval envelopes for Vaults no longer visible to the account are not opened or retained. A listed active Vault with no current-device envelope or no usable active-epoch key is an incomplete state and clients fail closed. `POST /api/v1/devices/{id}/revoke` revokes a device and its sessions.
- `PUT /api/v1/devices/capabilities` publishes a current-device report. The exact JSON body is `{account_id,device_id,revision,max_record_schema,host_attachment_manifest_versions,max_attachment_bytes,signature}`. `account_id` and `device_id` must match the authenticated principal; revision is a positive integer; `max_record_schema` is 1 or 2; manifest versions are a nonempty strictly ascending unique array containing only 1 or 2; `max_attachment_bytes` is an integer from 0 through 1073741824. The Ed25519 signature covers canonical JCS of exactly the six report data fields without `signature`, verified with the registered device signing key. A v1, missing, duplicate, or malformed marker cannot publish or restore a report asserting complete v2 support and returns `409 VAULT_CLIENT_CAPABILITY_REQUIRED`. A verified report replaces the previous report only at a higher revision. Exact same-revision replay returns `already_applied:true`; a lower revision or changed same-revision report returns `409 DEVICE_CAPABILITY_REVISION_CONFLICT`. A report that would remove schema-2, attachment-v2, or 1 GiB support from a device in any active schema-2 vault returns `409 DEVICE_CAPABILITY_REQUIRED`. Reports are also returned in `/api/v1/devices` and `/api/v1/vaults/{id}/devices`; the latter includes reports only for active devices of active members. `Current` means the latest accepted signed report for that device; reports do not expire by time. An absent report is effectively legacy schema 1 / attachment v1 / 256 MiB, and stale, invalid, or account/device/key-mismatched reports are not eligible for schema 2.
- **Implemented; focused acceptance passed:** `PUT /api/v1/devices/redaction-capabilities` is implemented for SQLite and the restricted PostgreSQL runtime. The SQLite route/OpenAPI/device-capability test group passed **32 tests**; focused PostgreSQL HTTP acceptance passed **2 tests**, including the report route and migration 25→29 restore helper; PostgreSQL repository and authentication invalidation unit tests passed **2 tests**; `cargo check --locked` passed. It accepts a separate current-device report with the exact body `{format,account_id,device_id,revision,sync_redaction_version,signature}`. `format` is `atermius-sync-redaction-capability-v1`, `sync_redaction_version` is integer `1`, and `revision` is a positive integer no greater than 9007199254740991. The report's Ed25519 signature is made by the registered current device signing key over UTF-8 JCS of exactly `{format,account_id,device_id,revision,sync_redaction_version}` (all report fields except `signature`). IDs must match the authenticated account and registered current device. The report route must contain exactly one `X-Atermius-Redaction-Marker: v1`; this unsigned transport declaration is independent of the signed report. After a report is published, the device must include exactly one v1 redaction marker on every authenticated request. If the server authenticates a request from that device without exactly one v1 marker, it marks the report inactive but preserves the signed revision floor. The same revision cannot reactivate an inactive report; a valid higher revision is required. A newly accepted higher revision replaces the current report; an exact retry at the same revision is idempotent only while the report remains active; a lower revision or a different valid signed report at the same revision returns `409 DEVICE_REDACTION_CAPABILITY_REVISION_CONFLICT`. Revision values may skip numbers but may never decrease. Missing/duplicate/non-v1 redaction markers return `400 INVALID_REDACTION_MARKER`; malformed, incorrectly signed, or authenticated-principal-mismatched bodies return `400 INVALID_DEVICE_REDACTION_CAPABILITY_REPORT`; inactive/revoked devices return `403 DEVICE_REVOKED`. The response includes `status:"stored"`, `already_applied`, and `redaction_capability_report`. This endpoint only records a device's protocol capability claim. The report is not proof that the client has received or applied redactions, does not verify local cache erasure, does not establish vault-wide compatibility, and does not authorize or trigger record purge. Any future purge endpoint must independently enforce its authorization, compatibility, retention, and transaction rules.
- Record redaction proofs, changes/history/conflict variants, snapshot graveyard entries, client apply order, and old-client gates are specified in [`RECORD-REDACTION-v1.md`](RECORD-REDACTION-v1.md) and implemented for SQLite and the restricted PostgreSQL runtime. Permanent purge is an explicit Vault Owner action; automatic tombstone purge remains disabled.
- `GET /api/v1/vaults/{id}/devices` requires current access to that vault and returns `{devices:[{device_id,user_id,name,signing_public_key,encryption_public_key,status,membership_status,created_at,capability_report}]}` for all devices of users with a current or historical membership row in that vault. `membership_status` is `active`, `invited`, `revoked`, or `archived`, independent of the device's `status`; clients count a report toward read compatibility only when both membership and device status are active. The signed report has the shape above for active devices of active members; revoked, archived, or inactive-member entries have `capability_report:null` and do not count toward compatibility gates. This public directory is needed to validate signatures on the vault's signed membership chain, key envelopes, and device capability claims; it contains no username or secret material. It includes revoked devices and former members' devices for historical signature verification. When an account is purged, public keys still referenced by a surviving shared vault are retained in a vault-scoped archive; those entries have status and membership_status archived, a synthetic name, and cannot authenticate.
- `GET /api/v1/vaults/{id}/members` returns `{members:[{user_id,username,role,state,added_at,invitation}]}`. `invitation` is `null` unless `state` is `invited`; then it is `{status,expires_at}`, where status is one of `pending`, `expired`, `stale`, or `reissue_required`. The server selects the latest unaccepted invitation by its private `issuance_order DESC`, then RFC3339 issuance timestamp and invitation ID; issuance order is not part of the DTO. Expiry takes precedence over key epoch or membership-version staleness. A pending status requires a non-null issuance order and timestamp, an unexpired token, a matching current epoch/membership version, and an active recipient device. Historical rows whose issuance order is `NULL` and invited members without an unaccepted invitation return `reissue_required` with `expires_at:null`; the server never guesses their expiry or relative order. A revoked or missing recipient device also returns `reissue_required` with `expires_at:null` because its device-bound token cannot be accepted. This directory never returns invitation tokens, token hashes, or key envelopes.
- `GET /api/v1/vaults` returns vaults where the caller has an active membership row, including vaults in deletion grace. Each item contains `{vault_id,role,active_key_epoch,membership_version,required_record_schema,status,requested_at,purge_after,can_cancel,can_write,name_envelope,key_envelopes}`. The floor starts at 1 and advances to 2 atomically with the first accepted schema-2 record or conflict branch; it never decreases. `status` is `active` or `deleting`; the time fields are RFC3339 UTC strings while deletion is pending and `null` while active. `can_cancel` is true only for an Owner before the deletion deadline. `can_write` is true only for a non-viewer while the vault is active. `name_envelope` is opaque ciphertext, and `key_envelopes` is an array addressed to the current device. A returned key-envelope item has `{recipient_device_id,key_epoch,membership_version,envelope,signature,signer_device_id}`. `envelope` is the opaque sealed-box object `{version,suite,ciphertext}`. Its signature covers `{vault_id,recipient_device_id,key_epoch,membership_version,envelope}` as specified below; `signer_device_id` identifies the registered public key the client must use to verify that signature and is transport metadata, not an unsigned replacement for signature verification. The client cross-checks the recipient, epoch, membership version and signer against the membership chain/device directory before opening it.
- `POST /api/v1/vaults` creates a client-generated vault with `{vault_id,name_envelope,key_envelope,membership}` using the corresponding `initial_vault` fields above. The server validates the signer device's Ed25519 signature over JCS of `{vault_id,membership_version,previous_digest,manifest}`, checks contiguous versions/roles/recipient membership, and stores the exact opaque name/key envelopes. The initial signer must be an active Owner; the first account's just-registered device is the only permitted bootstrap exception.
- Vault capacity defaults to 50 active membership Vaults per account and 100 active/invited members per Vault. `ATERMIUS_MAX_VAULTS_PER_USER` accepts 1–4096; `ATERMIUS_MAX_MEMBERS_PER_VAULT` accepts 1–1000. These settings are loaded at startup; invalid or out-of-range values fall back to defaults. Account counts include active memberships in active or deletion-grace Vaults; a pending invitation consumes no account slot until acceptance. Per-Vault counts include active and invited membership rows; revoked memberships do not count. `POST /api/v1/vaults` checks the account cap, invitation creation checks the target Vault cap, and `POST /api/v1/invitations/accept` checks both inside the same SQLite writer transaction as the state change. Capacity failures return `409 USER_VAULT_LIMIT_REACHED` or `409 VAULT_MEMBER_LIMIT_REACHED` and do not create a Vault, add a membership, or consume the invitation.
- `GET /api/v1/vaults/{id}/membership?from={version}` returns the signed membership chain. Each `manifests[].manifest` is the persisted signed-record DTO `{vault_id,membership_version,previous_digest,manifest,signature}`; clients validate its `vault_id` against the requested vault, verify the signature over JCS of `{vault_id,membership_version,previous_digest,manifest}`, and check monotonic versions. The registration/create-vault request's nested `membership` omits the outer `vault_id` because it is supplied by `initial_vault.vault_id`; the returned chain record always includes it. For databases created before this DTO was stored, the server adds the row's vault context when serializing the read response without changing the persisted digest, signature, or signed payload.
- `POST /api/v1/vaults/{id}/invitations` request includes `{role,recipient_device_id,recipient_encryption_public_key,key_envelope,membership,expires_in_seconds?}`; `expires_in_seconds` defaults to 604800 and must be in `[60,2592000]`. The server requires `recipient_encryption_public_key` to exactly match the registered target device and checks that the signed manifest's `encryption_key_fingerprint` equals base64url(SHA-256(decoded registered 32-byte key)). It implements one-use, expiring vault invitations. `POST /api/v1/invitations/accept` takes `{token}` in JSON, never in the URL. The owner-signed membership grant marks the recipient's role as `active`; the service keeps its access-control row `invited` until the recipient presents the matching token. Acceptance may activate access only while that grant's key epoch and membership version are still current, so a stale invitation must be refreshed by an owner. Recipient key material is sealed to the accepted device public key and signed by an existing owner. The recipient account must already be enrolled on this instance (using initial bootstrap or an operator-issued account invitation), and the vault invitation targets one of that account's active registered devices; vault invitations do not provision accounts. Out-of-range lifetime or key/fingerprint mismatch returns `400 INVALID_INVITATION_TTL` or `422 INVALID_ENVELOPE`, respectively.
- `POST /api/v1/vaults/{id}/keys/rotate` advances an epoch under the owner-signed rotation manifest and carries recipient-device key envelopes using the same signed envelope shape. Server state cannot create or decrypt a key envelope.
- `POST /api/v1/vaults/{id}/ownership/transfer` transfers ownership through the same signed membership chain and a mandatory key rotation. The authenticated current Owner signs a manifest containing `ownership_transfer: {from_user_id,to_user_id}`; the active target must already be an editor or viewer with at least one active device, and cannot be the current Owner, an invitee, a revoked member, or an inactive account. The former Owner remains an active editor, the target becomes the sole active Owner, and unrelated ACL changes cannot be combined with transfer. The request advances both membership version and key epoch by one and must include exactly one valid current-Owner-signed envelope for every active device in the retained membership. In one transaction the server commits the signed manifest, v1 display-name envelope, ACL roles, `vaults.owner_user_id`, epoch, and new key envelopes; stale versions or incomplete envelope sets leave all state unchanged. Pending invitations remain pending under the existing rotation rules and their old tokens become stale. Clients validate the transfer metadata against the preceding signed Owner and verify that only the source/target roles changed before accepting the chain. A committed `vault.ownership_transferred` audit event identifies the actor and target's opaque user ID, not a username.
- `DELETE /api/v1/vaults/{id}` begins the Owner-confirmed vault deletion grace period. Both this request and the cancel request require an active Owner device and JSON body `{ "login_verifier":"<base64url-no-pad 32-byte client-derived login verifier>" }`; the client sends its login verifier, never the master password. A bad proof returns `401 REAUTH_REQUIRED`. Each lifecycle proof attempt consumes the account's existing login rate-limit budget before Argon2 verification; over-limit responses use `429 RATE_LIMITED` with `Retry-After`. Success returns `{vault_id,role,status:"deleting",requested_at,purge_after,can_cancel,can_write:false}` with RFC3339 UTC timestamps. Repeating DELETE while pending is idempotent and returns the original deadline without extending it. All active members immediately lose write access, but can continue to list the vault, read its member/device directory and signed membership, pull changes, create/read snapshots, page encrypted revisions and conflict branches from one snapshot, fetch a single encrypted revision and download encrypted objects. These APIs let clients read their ciphertext during the grace period and provide primitives for client-side export; the server does not implement a portable export package workflow. Data/member writes against a deleting vault return `409 VAULT_DELETION_PENDING`, including invitation acceptance, key rotation, device enrollment that would transfer its vault keys, record/conflict writes, and object upload/finalization. These state checks are repeated after acquiring the SQLite write transaction so a concurrent delete/cancel/purge is serialized with the operation. `POST /api/v1/vaults/{id}/deletion/cancel` takes the same reauthentication body and returns `{vault_id,role,status:"active",requested_at:null,purge_after:null,can_cancel:false,can_write:true}`; an already-active vault returns the same active DTO. Cancellation succeeds only before `purge_after`; at or after the deadline, before the maintenance purge runs, it returns `410 VAULT_DELETION_WINDOW_EXPIRED`. Once the vault has been purged, its resource routes return `404 NOT_FOUND`.
- Vault-scoped routes use the same generic `404 NOT_FOUND` for a missing vault and a vault the caller does not belong to, preventing vault-ID enumeration. After final purge, reads and writes therefore return the same 404 as any other unavailable vault. A current member whose role prevents a requested operation still receives the corresponding role error.

The default vault deletion grace is 604800 seconds (7 days). `ATERMIUS_VAULT_DELETION_GRACE_SECONDS` accepts 60 through 7776000 seconds (90 days); invalid or out-of-range values use the default. Maintenance atomically purges due vaults and their records, versions, graveyard, conflicts, snapshots, encrypted objects/uploads, invitations, key envelopes and membership chain. The deletion ledger stores the opaque vault ID, request/deadline/cancel/purge timestamps, and a domain-separated HMAC of the requesting account+device IDs; it does not store usernames, raw account/device IDs, verifier, session secrets or ciphertext. Completed/cancelled audit entries are retained for `ATERMIUS_AUDIT_RETENTION_DAYS` (default 365, valid range 1..3650); pending deletion rows are never removed by audit retention. Database and object backups can retain bytes according to their own configured retention after the live vault is purged.

Membership display metadata follows the signed epoch chain. New clients include `manifest.display_name_envelope` in the initial signed manifest, using the same ciphertext as the top-level `name_envelope`; the server requires equality when that signed field is present. The top-level envelope always passes the bounded v1 shape check, while old initial signed manifests without the inner field remain accepted. New clients include the field in each invitation membership manifest, encrypted with the current epoch key, and in every key rotation manifest, encrypted with the new epoch key. The signature continues to cover the complete `{vault_id,membership_version,previous_digest,manifest}` payload. The server validates the v1 shape (exact keys `version`, `nonce`, `ciphertext`; version 1; base64url-no-pad nonce exactly 24 bytes; ciphertext 16 bytes through 48 KiB; envelope at most 64 KiB) and mirrors any present value into `vaults.name_envelope` inside the same transaction. Rotation requires this field; legacy invitation requests may omit it and preserve the stored envelope. Legacy chains without the field remain readable using the top-level envelope.

## Encrypted records and sync

An encrypted record envelope is:

```json
{
  "header": {
    "wire_version":1,"server_space_id":"uuid","vault_id":"uuid","record_id":"uuid",
    "revision_id":"uuid","base_revision_id":null,"op_id":"uuid","device_id":"uuid",
    "device_seq":"1","key_epoch":"1","membership_version":"1","record_schema":1,
    "operation":"create","crypto_suite":"atermius-vault-v1","kdf_salt":"base64url",
    "object_refs":["00000000-0000-0000-0000-000000000001"]
  },
  "nonce":"base64url-24-bytes",
  "ciphertext":"base64url-aead-output",
  "signature":"base64url-ed25519-signature"
}
```

Record plaintext remains opaque; record type and all business fields are inside ciphertext. AEAD AAD is UTF-8 RFC 8785 JCS of `header`. The Ed25519 signature covers UTF-8 JCS of `{header,nonce,ciphertext}`. Every field affecting authorization or routing must be authenticated. The optional `header.object_refs` is a strictly ascending, duplicate-free array of at most 1024 lowercase canonical UUID strings; omission is equivalent to `[]`. That maximum array is about 40 KiB, within the 64 KiB header and 1 MiB request limits. Because it is part of `header`, it participates in both JCS AAD and the envelope signature. Clients check it against the encrypted manifest.

`POST /api/v1/vaults/{id}/sync/push` body `{protocol_version,server_generation,vault_id,device_id,batch_id,operations:[envelope...]}`. A batch is atomic. Record schemas 1 and 2 are accepted; unknown schemas are rejected as invalid envelopes. A schema-2 operation is accepted only when, in the same SQLite writer transaction, every active device of every active member of that vault has a latest verified report with `max_record_schema>=2`, `host_attachment_manifest_versions` containing 2, and `max_attachment_bytes>=1073741824`. Missing, stale, or incompatible reports fail closed as v1 and return generic `409 VAULT_CLIENT_CAPABILITY_REQUIRED`; there are no device IDs in the error. The gate applies to new operations and to schema-2 conflict branches. When a schema-2 operation or conflict is accepted, `required_record_schema` advances to 2 in that same transaction and never decreases. New devices cannot be enrolled into a floor-2 vault and invitations cannot be accepted there unless the candidate/all active recipient devices meet the same report requirements. Success returns `{batch_id,results:[{op_id,revision_id,commit_seq,already_committed}]}`. The server checks the stored result for a valid retry before requiring the current key epoch. For each new revision, every `object_refs` entry must identify an already completed object in the same vault. Missing, cross-vault, open-upload, expired-upload, and otherwise unavailable IDs all return the same `409 OBJECT_REFERENCE_UNAVAILABLE`; the batch creates no revision, event, head, receipt, or reference. A successful revision stores the explicit `(vault_id,revision_id,object_id)` references and clears those objects' pending GC deadline in the same writer transaction. Exact retries remain idempotent. `REVISION_CONFLICT` includes the current opaque revision envelope only when access permits. Reusing an operation or sequence ID with a different request digest is rejected.

`revision_id` is unique across its entire Vault, matching the immutable revision read key `(vault_id,revision_id)`; reuse returns `409 REVISION_EXISTS` and rolls back the whole batch. Legacy databases may contain duplicate IDs on different records because their historical uniqueness key included `record_id`. A single-revision read detects that state and returns `500 INTERNAL` rather than returning an arbitrary record. New writes cannot add further duplicates.

For stale offline outbox recovery, the stored exact operation receipt takes precedence over current key epoch and membership version checks, after the server has validated the current server generation, caller session/device and active write authorization. A successful exact receipt proves that operation committed and must be applied to the old local outbox row without changing its envelope or IDs. If an atomic multi-operation batch returns `409 KEY_EPOCH_OUTDATED` or `409 MEMBERSHIP_VERSION_CONFLICT`, that batch response has no per-operation commit result: the client must retry each original signed envelope individually with a fresh batch ID. Only the same individual operation receiving one of these specific stale-version errors proves that that exact operation was not committed. Network errors, timeouts, 5xx, `SERVER_GENERATION_CHANGED`, snapshot absence, and other failures are not proof of non-commit and must not trigger re-encryption. A read-only, revoked, or otherwise non-writable device must retain its encrypted local outbox without re-signing.

After a definitive per-operation stale-version rejection and a fresh verified reload of the Vault descriptor, signed membership chain, and current key envelopes, an active writable client may rewrap the uncommitted operation chain for the same record. This permission is limited to one push pass and is cleared on snapshot-recovery failure as well. It verifies each old signature and decrypts with the original epoch key, pulls/reconciles current state, and re-encrypts against current `key_epoch` and `membership_version`. A competing head is handled through the normal conflict flow; it is not blindly rebased. Every replacement receives a fresh `op_id`, `revision_id`, `device_seq`, nonce, and signature. The prior signed envelopes remain immutable local history with a non-pushable `superseded` status; replacement rows and the optimistic record head are committed in one local database transaction. If an old key is unavailable, signature/decryption fails, or current write authorization cannot be established, the client fails closed and preserves the original outbox.

`GET /api/v1/vaults/{id}/changes?cursor={opaque}&limit=500` returns `{events:[{commit_seq,event_type,envelope}],next_cursor,has_more,server_generation}`. The cursor is at most 2048 bytes; the complete raw query string is capped at 2112 bytes before authentication and Axum query extraction, and an oversized query returns `400 INVALID_CURSOR`. For an in-bound query, authentication and active Vault membership are checked before parsing the cursor; membership is checked again for every page. A valid cursor is an authenticated opaque token bound to the vault and server generation, and represents only the fully returned ordered prefix. A valid cursor for another Vault/version is `400 INVALID_CURSOR`; an authenticated cursor from another generation is `410 CURSOR_EXPIRED`. To recover when a physical restore also rolled back the cursor HMAC key, a bounded canonical cursor payload for this route that claims a different canonical generation may also receive `410 CURSOR_EXPIRED` with `{recovery:"create_snapshot",preserve_local_outbox:true}` even when its MAC cannot be verified. This is only a recovery hint: the claimed sequence is never trusted or used, no page is returned, and the response does not prove the cursor was issued by the server. Same-generation tampering, malformed/noncanonical payloads, and wrong-Vault claims remain `400 INVALID_CURSOR`. Each page is read from one SQLite transaction that checks active membership and reads the high watermark, retention floor, and event rows together; rows are also bounded by that captured high watermark.

`POST /api/v1/vaults/{id}/snapshots` captures both `high_watermark` (record commit sequence) and `conflict_high_watermark` (conflict create/resolve sequence) in the same writer transaction, persists each current head as an immutable snapshot item, and returns both watermarks as decimal strings plus `item_count` (the number of captured heads). Snapshot creation streams the fixed head set and does not materialize a large Vault in memory. Each item must fit within one 4 MiB response page including metadata; an individually oversized/corrupt item returns `413 PAYLOAD_TOO_LARGE` and the transaction stores no snapshot. Snapshot items expire after 24 hours and reads then return `410 SNAPSHOT_EXPIRED`. The current SQLite runtime maintenance deletes expired child payload rows but retains parent metadata for that response. PostgreSQL snapshot reads enforce expiry, but PostgreSQL runtime maintenance is not wired yet and must add equivalent child-row cleanup before PG production mode is enabled.

`GET /api/v1/snapshots/{id}` without `limit` and `page_cursor` preserves the legacy full-manifest response shape and behavior. It returns the fixed manifest only when the complete serialized response is at most **4 MiB**; a larger manifest returns `413 PAYLOAD_TOO_LARGE` with `{max_response_bytes:4194304,recovery:"contact_server_operator"}`. The server can page the full captured manifest, subject to its per-item limits. The current Flutter recovery and portable-export clients cap the aggregate serialized manifest at 64 MiB or 100,000 heads. Exceeding either client cap stops the operation with `snapshot_too_large`: recovery does not apply a partial snapshot or change the local checkpoint/outbox, and export returns no partial archive. Durable local page staging is not implemented. The Flutter client requests pages with `GET /api/v1/snapshots/{id}?limit=100&page_cursor={opaque}`. `limit` is 1 through 500; it defaults to 100 only when a `page_cursor` is supplied without a limit. The first page omits `page_cursor`. Each page response is `{snapshot_id,high_watermark,conflict_high_watermark,item_count,next_cursor,expires_at,manifest,has_more,next_page_cursor}`: `item_count` is the captured total number of heads; `manifest` contains at most `limit` current-head items ordered by binary `record_id`; `next_cursor` remains the changes-feed cursor at `high_watermark`; and `next_page_cursor` is opaque or null. A page is at most 4 MiB including its JSON wrapper; if a single item cannot fit, the server returns 413 without advancing. The HMAC page cursor is domain-separated and bound to the snapshot ID, Vault ID, server generation, and last returned `record_id`; malformed, altered, noncanonical, wrong-snapshot, or wrong-Vault cursors return `400 INVALID_CURSOR`. A cursor from another server generation or an expired snapshot returns `410 SNAPSHOT_EXPIRED`. Clients continue until `has_more=false`, require `next_page_cursor=null` on that final page, and verify that the number of received distinct record IDs equals `item_count` before accepting bootstrap. Each page rechecks current Vault membership and session/device validity.

Existing clients can ignore the added `item_count`; an old snapshot created before this migration has `conflict_high_watermark:null`, and its original manifest and changes-cursor behavior remains unchanged. Migration 0044 backfills page rows from retained legacy manifests without changing those manifests. Snapshot item keyset ordering uses SQLite BINARY or PostgreSQL C collation, and every item row contains the exact captured envelope so later head changes cannot alter an in-progress bootstrap.

`GET /api/v1/vaults/{id}/revisions?snapshot_id={uuid}&cursor={opaque}&limit=500` reads the complete immutable revision history in ascending per-vault `commit_seq` order, bounded by the supplied snapshot's `high_watermark`. It returns `{snapshot_id,vault_id,high_watermark,conflict_high_watermark,revisions:[{record_id,revision_id,base_revision_id,commit_seq,operation,deleted,created_at,restore_until,envelope}],next_cursor,has_more,server_generation}`. `high_watermark` and `commit_seq` are decimal strings. `deleted` means this particular immutable revision is a tombstone (`operation:"delete"`), even if a later revision restored the record. `restore_until` is optional rollout-compatible RFC3339 date-time metadata; current servers include the key, with a timestamp for delete revisions and null for other operations (including redacted rows). Older servers may omit it. The exact signed envelope is returned without decryption, including any `header.object_refs`. Revisions are not pruned by change-event retention. The old `GET /api/v1/vaults/{id}/revisions/{revision_id}` response remains unchanged.

`GET /api/v1/vaults/{id}/conflicts?snapshot_id={uuid}&cursor={opaque}&limit=500` reads immutable conflict branch envelopes in ascending per-vault `conflict_seq` order, bounded by the same snapshot's `conflict_high_watermark`, and returns `{snapshot_id,vault_id,high_watermark,conflict_high_watermark,conflicts:[{conflict_id,conflict_seq,record_id,base_revision_id,resolved_revision_id,resolution_seq,created_at,envelope}],next_cursor,has_more,server_generation}`. Watermarks, `conflict_seq`, and non-null `resolution_seq` are decimal strings. Each conflict creation and each first successful resolution transition advance a per-vault sequence atomically; resolution retries do not allocate a sequence. Branches created after the snapshot are excluded, and a resolution with `resolution_seq > conflict_high_watermark` is represented as unresolved. Existing rows are backfilled during migration in deterministic creation/resolution order. The exact encrypted envelope, including `header.object_refs`, is returned unchanged. Conflict branch envelopes are immutable and retained with their object references.

`GET /api/v1/vaults/{id}/conflict-changes?after_seq=0&limit=100&server_generation={uuid}` is the append-only incremental conflict inbox feed. `after_seq` is an optional canonical non-negative decimal string defaulting to `"0"`; omit it for the first request when no checkpoint exists. `limit` defaults to 100 and must be in `[1,500]`. The first request may omit `server_generation`; every continuation that explicitly supplies `after_seq`, including `after_seq=0`, must send the `server_generation` returned by its preceding page. Every request rechecks current active vault membership (read-only members may read) and reads `last_conflict_seq` plus the page rows in one transaction. Each response is `{vault_id,after_seq,high_watermark,events,next_after_seq,has_more,server_generation}`; all sequence values are decimal strings. Events are ordered by sequence and contain `{seq,type,conflict_id,record_id,base_revision_id,resolved_revision_id,created_at}`. `type` is `created` or `resolved`; `base_revision_id` may be null. Created events set `resolved_revision_id:null` and include the exact original `envelope`; resolved events include the non-null `resolved_revision_id` and omit `envelope`. `created_at` is the creation time for a created event and the first successful resolution time for a resolved event. Migration 0015 records `resolution_at`; for older resolved rows, the feed uses the resolved revision's `created_at`, falling back to the conflict's `created_at`. `high_watermark` is read with the page and may advance on a later continuation page. `has_more` only describes rows after `next_after_seq` through that response's watermark; events committed afterward remain available to the next request. Empty pages echo `after_seq` in `next_after_seq`. A non-canonical/negative/overflowing sequence returns `400 INVALID_AFTER_SEQ`; a continuation without `server_generation` returns `400 SERVER_GENERATION_REQUIRED`; an invalid generation UUID returns `400 INVALID_SERVER_GENERATION`; and an invalid limit returns `400 INVALID_LIMIT`. A generation mismatch returns `410 CONFLICT_FEED_GENERATION_CHANGED` with `{server_generation,current_generation,recovery:"restart_from_zero"}`; an `after_seq` beyond the current watermark returns `410 CONFLICT_FEED_SEQUENCE_AHEAD` with `{recovery:"restart_from_zero"}`. Clients restart the feed at zero after a generation change while retaining any old-generation local inbox in its original generation scope. This endpoint is distinct from snapshot-bound `/conflicts`, which remains the immutable archive/history reader.

For `GET /changes`, `GET /snapshots/{id}`, `GET /revisions`, `GET /conflicts`, and `GET /conflict-changes`, the complete raw query string is capped at **2112 bytes** before authentication and Axum query extraction. An oversized query returns a fixed `400 INVALID_CURSOR` response without echoing the query. This applies to the GET `/conflicts` history route; `POST /conflicts` is unchanged.

All four ordered pull/history pages (`/changes`, `/revisions`, `/conflicts`, and `/conflict-changes`) have a **4 MiB maximum serialized JSON response**, including the wrapper. `limit` remains a maximum of 500 rows; a server may return a shorter ordered prefix when the byte budget is reached. `has_more` is true when another row exists, and every cursor/`next_after_seq` points to the last row actually returned, never the first omitted row. If a single first row cannot fit, the endpoint returns `413 PAYLOAD_TOO_LARGE` with `details.max_response_bytes` and `details.recovery:"contact_server_operator"`; it returns no partial page and does not advance the checkpoint. Current write limits keep one signed envelope below this page maximum, so this error is a fail-closed guard for oversized legacy or corrupted rows.

Both history endpoints require the same newly created `snapshot_id`, giving the client one paired boundary across record revisions and conflict branches; the snapshot endpoint itself remains a current-head manifest, not the history page. A legacy snapshot without a conflict watermark is still readable through its original snapshot route, but both history pages return `409 HISTORY_SNAPSHOT_INCOMPLETE` with `{recovery:"create_new_snapshot"}`. Both history cursors are authenticated opaque tokens bound to the vault, server generation, history kind, snapshot ID, both fixed watermarks, and last returned sequence. The default page size is 500; `limit` must be in `[1,500]`, otherwise the server returns `400 INVALID_LIMIT`. Invalid/tampered, wrong-vault, or wrong-kind cursors return `400 INVALID_CURSOR`; a cursor from a prior server generation against a current snapshot returns `410 HISTORY_CURSOR_EXPIRED` with `{recovery:"create_new_snapshot"}`. A snapshot created by a prior generation returns `410 SNAPSHOT_EXPIRED`. Every page rechecks current vault membership and is readable by active members during vault deletion grace. Once final purge removes the vault, these endpoints return the same generic `404 NOT_FOUND` as any unavailable vault. A missing or non-canonical snapshot ID returns `400 INVALID_SNAPSHOT_ID`. An unavailable or foreign snapshot ID normally returns generic `404 NOT_FOUND`. If a physical restore removed a prior-generation snapshot row, a continuation request whose cursor is a canonical v1 history-cursor claim matching the requested vault, snapshot ID, and endpoint kind, with canonical decimal watermark/position fields and a canonical generation different from the current one, returns `410 HISTORY_CURSOR_EXPIRED` with `{recovery:"create_new_snapshot"}`. This unverified generation claim is only a recovery hint: its MAC is not authenticated because the prior key may have been physically rolled back; none of its watermarks or position is used and no history rows are read. Active session and Vault membership checks happen first. Missing or foreign snapshots without a matching typed foreign-generation claim retain generic `404 NOT_FOUND`.

Snapshots expire after 24 hours and are bound to the server generation that created them. The manifest returned by `GET /api/v1/snapshots/{id}` remains a fixed current-head view; use the snapshot-bound revision and conflict pages above for complete history. Snapshot IDs do not grant access by themselves: every manifest/history read checks the caller's current vault membership.

During rollout, existing tombstones are backfilled using the effective valid `ATERMIUS_RECORD_RESTORE_RETENTION_DAYS` setting at upgrade time. This preserves the cutoff the old server would advertise at that moment; the old schema did not retain per-delete configuration history, so an earlier per-delete value cannot be reconstructed. When restoring a backup, legacy tombstones are backfilled using the restore-retention value recorded in that archive's runtime-policy manifest, not a different target setting accepted through policy-drift override. New tombstones keep their stored deadline across later configuration changes. Automatic time-based tombstone purge remains disabled; the deadline metadata does not trigger deletion, and permanent purge remains an explicit owner action.

The server retains change-event history for 90 days by default; `ATERMIUS_HISTORY_RETENTION_DAYS` can set 1 through 3650 days. Retention prunes only a contiguous prefix of each vault's ordered `commit_seq` stream, so timestamps moving backwards cannot create holes. When the first retained event is sequence `minimum_available_seq`, cursors before `minimum_available_seq - 1` return `410 CURSOR_EXPIRED` with `{recovery:"create_snapshot",preserve_local_outbox:true}`. The client must preserve its local outbox, fetch a fresh snapshot, then resume from the returned `next_cursor`. A 410 caused by an unverifiable foreign-generation claim is a recovery hint rather than proof that the cursor is authentic. Record revisions, current heads and tombstone graveyard entries are not pruned by this history job.

`atermius-server maintenance` runs the same expiration pass used hourly by the serving process: it prunes expired change-event prefixes, clears expired snapshot manifests while keeping metadata for a `SNAPSHOT_EXPIRED` response, marks expired uploads while deleting their chunk payloads, purges vaults whose deletion deadline has passed, sweeps due unreferenced encrypted objects, and prunes terminal deletion audit rows past their retention. Pending deletion rows are excluded from audit pruning. It does not delete immutable record history or any object referenced by an extant record revision or conflict branch.

The built-in `atermius-server restore` workflow stages a validated backup into a **new** data directory and writes a new `instance_meta.generation` while revoking restored sessions before publishing it. It requires the current data directory to be server-stopped and locked; it never replaces the current data directory. The operator switches the deployment to the staged directory only after the command succeeds. This makes prior cursors and snapshots expire while clients retain their outbox. For an older database restored manually outside this workflow, stop the server and run `atermius-server recover-generation --server-stopped` against that database; this acquires `server.lock`, fails with `SERVER_RUNNING` if `serve` still owns the directory, changes the instance generation, and leaves instance/server-space IDs and the cursor signing key unchanged.

Instance backup is an operator CLI workflow rather than an HTTP endpoint. The server creates a missing final data directory with Unix mode 0700 and requires an existing directory to already be a dedicated mode-0700 directory; it rejects a symlink or shared/system directory rather than changing that directory's permissions. Ancestors may not be group/world-writable unless they use the sticky bit (as `/tmp` does). The database and `server.lock` are stored inside this boundary; the lock file is mode 0600 and rejects symlinks. All server commands support only SQLite at `ATERMIUS_DATA_DIR/atermius.db`; custom/external `ATERMIUS_DATABASE_URL` values are rejected. Bind-mounted directories must be provisioned with mode 0700 and writable by the service UID. `atermius-server backup --archive <path> --key-file <path>` uses SQLite `VACUUM INTO` for a WAL-safe consistent snapshot. The key file and backup archive must be outside the active data directory and kept under separate access controls; the archive should be moved to off-host storage while the key remains in a separate secrets or offline store. The version-1 encrypted archive contains exactly `database.sqlite`, `instance-ed25519.key`, and `auth-rate-limit.key`; its canonical JCS manifest records each file's size and SHA-256 plus a non-secret runtime-policy summary, including Relay CIDR and exact destination-port allowlists when configured. Empty Relay port lists are omitted for compatibility with existing version-1 backup manifests. A separate owner-only 32-byte backup key is mandatory, is never included, and encrypts the manifest and every 1 MiB file chunk with XChaCha20-Poly1305. Unknown/missing archive files, noncanonical manifests, failed authentication, checksum errors, truncation, unsupported schema, SQLite integrity errors, and foreign-key violations are rejected before publication.

`atermius-server restore --archive <path> --key-file <path> --target-data-dir <new-path> --server-stopped` verifies the OS-level lock for the current `ATERMIUS_DATA_DIR`, requires both archive and operator key to be outside that directory, restores only to a destination that does not already exist, migrates and validates the staged database, rotates generation, revokes restored sessions, and atomically publishes the complete directory. The existing directory remains intact for rollback; the operator must switch the deployment's `/data` mount to the new path and restart only after checking the printed generation. Database rows, including encrypted objects, are restored from the SQLite snapshot. The encrypted archive records runtime policy values for comparison, but deployment environment/configuration (including `.env`, TLS/reverse-proxy settings, host port and volume selection) is a separate required recovery artifact; keep it with the backup under the same offline protection policy. The restored process uses the environment supplied when it starts.

`instance-ed25519.key` and `auth-rate-limit.key` are atomically created as private 32-byte files with Unix mode 0600. Existing files must be regular files without group/other permissions or symlink indirection; an unsafe legacy file prevents startup until the operator secures or replaces it. Back up both files alongside the database; replacing the auth limiter key resets anonymous rate-limit buckets after restart.

- Delete is a signed encrypted `operation:"delete"` revision and updates a compact graveyard entry.
- Restore is an explicit `operation:"restore"` CAS against the current tombstone. A delete revision fixes `restore_until` at commit time from its `created_at` and the effective `record_restore_retention_days` setting, default 30 days and configurable with `ATERMIUS_RECORD_RESTORE_RETENTION_DAYS` (range 1..3650). Later setting changes do not move a deadline already fixed on a tombstone. On startup, legacy delete revisions without a stored deadline are backfilled from the policy the old server currently advertises, preserving the cutoff clients see immediately before upgrade; legacy archive rows use the archived runtime policy. `GET /api/v1/instance` advertises the effective setting for new deletes; an expired restore returns `409 RECORD_RESTORE_EXPIRED` with `{recovery:"create_new_record",restore_retention_days,restore_until,restore_expires_at}`, where the old `restore_expires_at` is a compatibility alias. The graveyard remains reserved, so clients must create a new record with a new ID after expiry.
- `POST /api/v1/vaults/{id}/conflicts` takes `{envelope}` and stores a signed encrypted non-head branch. Its idempotency key is the signed `header.op_id`, scoped to `(vault_id, device_id)`. A schema-2 branch uses the same all-active-reader capability gate as sync push and atomically raises `required_record_schema` to 2. A retry with the same JCS envelope digest returns the original `conflict_id` and response without allocating a sequence or writing references again. Reusing that key with a different digest returns `409 IDEMPOTENCY_KEY_REUSED`. It validates and stores `header.object_refs` in the same transaction; unavailable object references return `409 OBJECT_REFERENCE_UNAVAILABLE`. Migration backfills one deterministic canonical key per legacy `(vault, device, op_id)` group; preexisting duplicate branch rows remain in readable history while only the earliest row claims the key. `POST /api/v1/vaults/{id}/conflicts/{cid}/resolve` attaches its resolution to an already committed new main revision. The first successful resolution emits one `vault.conflict_resolved` Vault audit event with only the opaque conflict ID and authenticated actor; same-revision retries do not duplicate it, and audit insertion failure rolls back the resolution.
- Conflict resolution's first success returns `{status:"resolved",resolved_revision_id,resolution_seq,already_resolved:false}` and stores `resolution_at` in the same transaction as `resolution_seq` and `resolved_revision_id` for the incremental event feed. Repeating the same `resolved_revision_id` returns `200` with the original non-null decimal-string `resolution_seq` and `already_resolved:true`, even if the main head advanced after the original response was lost; it does not increment the conflict sequence. Trying a different resolution after one was recorded returns `409 CONFLICT_ALREADY_RESOLVED`.

### Permanent record redaction and purge

`PUT /api/v1/devices/redaction-capabilities` publishes a device-signed support declaration. That declaration does not prove the device has applied a redaction and does not grant purge authorization. Before purge, every active device of every active Vault member must have a currently valid report for redaction protocol v1; offline active devices count. The server rechecks reports, Owner membership, the current tombstone and its persisted `restore_until`, unresolved conflicts, snapshot state, and object-reference ownership inside the same Vault writer fence as sync writes and snapshot creation.

`POST /api/v1/vaults/{vault_id}/records/{record_id}/purge` requires an active Vault Owner session and exactly one `X-Atermius-Redaction-Marker: v1`. The exact request body is `{expected_deleted_revision_id,expected_deleted_seq}`, bound to the deleted revision and commit sequence currently shown by the recycle-bin snapshot. Success returns `{status:"purged",already_purged,redaction}` with a signed `atermius-record-redaction-proof-v1` statement; an exact retry returns the original statement. Typical failures are `403 VAULT_OWNER_REQUIRED`, `409 RECORD_PURGE_NOT_DUE`, `RECORD_DELETE_CHANGED`, `RECORD_HAS_UNRESOLVED_CONFLICTS`, `REDACTION_REFERENCE_AMBIGUOUS`, or `VAULT_REDACTION_CAPABILITY_REQUIRED`, and `426 CLIENT_REDACTION_CAPABILITY_REQUIRED` for an unsupported client marker. A purge scrubs active revision/event/resolved-conflict payloads while preserving ordering positions and record-ID reservation, invalidates existing snapshot pages, and schedules newly unreferenced objects through the configured delayed collector. It does not erase offline device copies or older encrypted backups; restoring a pre-purge backup can restore ciphertext.

`PUT /api/v1/vaults/{vault_id}/records/{record_id}/automatic-purge` stores consent for one exact tombstone. Its strict body is `{expected_deleted_revision_id,expected_deleted_seq,expected_policy_revision,enabled}`; the path and expected tombstone identity must still identify the current retained delete head, and `expected_policy_revision` is a canonical non-negative decimal string used for compare-and-set. Only the active Vault Owner may change the policy. A device with a published redaction-capability report must send exactly one canonical v1 redaction marker on this authenticated request. PostgreSQL also requires the caller's current redaction-capability report when the Vault already contains a redacted record. A changed `enabled` value increments `policy_revision` and writes the Vault audit action `vault.record_auto_purge_opt_in_changed` from source `api`; repeating the current value is idempotent and does not duplicate the audit event. The response is `{vault_id,record_id,deleted_revision_id,deleted_seq,enabled,policy_revision}`. Stale tombstone identity returns `409 RECORD_TOMBSTONE_CHANGED`; a stale policy revision returns `409 RECORD_AUTO_PURGE_POLICY_REVISION_CONFLICT` with the current revision in error details. Consent defaults to false and does not move `restore_until` or purge immediately. Re-enabling after an opt-out advances the policy revision. Restoring removes the tombstone policy, and a later delete starts disabled at revision 0. An explicit purge consumes enabled consent and resets it to disabled, advancing the revision when the prior state was enabled. No automatic purge worker or scheduler currently runs; any future Maintenance purge must recheck the exact tombstone policy and all existing purge gates inside its transaction. Manual Owner purge remains a separate explicit action.

Unredacted delete entries in revision history may include `auto_purge_enabled` (boolean) and `auto_purge_revision` (canonical decimal string). They are omitted for non-delete and redacted rows and may be omitted by older servers. These current policy values are read-time metadata outside the snapshot sequence watermark and can change while history pages are read; they do not prove that a revision is the current tombstone or is otherwise purgeable. Backups preserve exact policy state when available, but restore opts any enabled policy out; legacy backups without this state remain opted out. Consent does not erase offline device copies or earlier encrypted backups, and restoring a pre-purge backup may restore ciphertext.

## Objects, notifications and relay

- `POST /api/v1/vaults/{id}/uploads/init` reserves quota and returns `{upload_id,chunk_size,expires_at}`. Initialization is idempotent for the same authenticated user and `(vault_id,object_id,size,sha256)`: while an open reservation is unexpired, retrying after a lost response returns the same upload ID and expiry without reserving quota again. SHA-256 comparison is case-insensitive after the request digest is normalized. Reusing an active object ID with different size/hash returns `409 UPLOAD_RESERVATION_CONFLICT`; if another member owns an active reservation, the server returns generic `409 UPLOAD_IN_PROGRESS` and does not disclose or transfer that member's upload ID. Expired reservations are not reused; a new init marks matching expired rows terminal and deletes their temporary chunks before making a new reservation. An already completed object ID returns `409 OBJECT_EXISTS`. Upload tickets remain bound to the initiating user. There is no remote abort operation: discarding a local upload leaves its reservation and quota reserved until its 24-hour TTL expires. `PUT /api/v1/uploads/{upload}/chunks/{index}` stores immutable opaque bytes. `POST /api/v1/uploads/{upload}/complete` verifies and assembles the object, returns chunk receipts, and deletes temporary chunk payloads in the same transaction. A repeated completion returns the object receipt while the object exists; after collection it returns `410 OBJECT_COLLECTED`. `GET /api/v1/vaults/{id}/objects/{object_id}` retrieves bytes after current authorization; after collection it returns the same generic `404 NOT_FOUND` as an unknown object. Responses include a strong SHA-256 `ETag` and `Accept-Ranges: bytes`; no `Range` request remains HTTP 200 with the complete opaque object and `Content-Length`. One byte range is supported: `bytes=start-end`, `bytes=start-`, and `bytes=-suffix-length` return 206 with `Content-Range` and the selected opaque bytes. The requested end is clipped to the object size. Unknown Range units are ignored and return the full object. Malformed or unsatisfiable byte ranges, repeated `Range` headers, and multi-range requests return an empty standard HTTP 416 response with `Content-Range: bytes */<size>`. A single exact strong `If-Range` ETag allows the range; a stale, weak, date, or repeated `If-Range` validator causes the server to ignore Range and return the complete HTTP 200 representation. Range parsing happens only after normal vault authorization and object lookup, so 416 metadata is not available to unauthorized callers.
- Object blocks are encrypted client side and immutable. The service checks size/hash/quota but never parses the encrypted manifest. A newly completed object receives a GC deadline seven days later by default; `ATERMIUS_OBJECT_GC_GRACE_SECONDS` accepts 60 through 7776000 seconds (90 days), with invalid values falling back to the default. A successful record or conflict reference cancels that deadline. Hourly/operator maintenance deletes an object only after its deadline and only if no extant `object_references` row points to it; the reachability check and delete are serialized in one SQLite writer transaction. Current heads, immutable historical revisions, conflicts, and snapshots therefore keep their referenced objects. Existing blob rows from before this migration have `gc_after=NULL` and are retained indefinitely until explicitly referenced or the vault is deleted, avoiding accidental collection of legacy data. Collected completed uploads transition to terminal `state='collected'`; this releases quota and any remaining chunk payloads.
- Low-latency sync notifications are optional and enabled only when `ATERMIUS_PUBLIC_ORIGIN` is set. `POST /api/v1/notifications/tickets` requires the normal bearer session and has no request fields. It returns `{ticket,expires_at,expires_in_seconds}`; `ticket` is a random 32-byte base64url-no-pad value, valid for at most 30 seconds and never placed in a URL. The database stores only its SHA-256 hash. A ticket is atomically consumed once and bound to the issuing user, device, session, server generation, and the session's exact access-expiry timestamp. Session refresh, logout, device revocation, account deletion, ticket expiry, or a prior-generation restore makes it unusable. Independent pending tickets allow multiple browser tabs; issuance is limited to 30 per user/minute and 10 per session/minute. Disabled notifications return `503 NOTIFICATIONS_DISABLED`; issuance throttling returns `429 NOTIFICATION_TICKET_RATE_LIMITED` with `Retry-After`; ticket-store capacity returns `503 NOTIFICATIONS_BUSY`.

- Mobile background sync hints use `PUT /api/v1/notifications/push-endpoints/{device_id}` and `DELETE /api/v1/notifications/push-endpoints/{device_id}/{provider}`. Registration requires the active bearer session and exact current device ID; a mismatch returns `403 DEVICE_MISMATCH`. The body is `{provider,token}`, where provider is `fcm_v1` or `apns`. FCM tokens must contain 16–4096 printable non-space ASCII bytes. APNs device tokens must be 32–512 ASCII hexadecimal characters, in byte pairs. The JSON extractor rejects malformed JSON, unknown fields, and unknown provider enum values with `422`; an invalid token returns `400 INVALID_PUSH_ENDPOINT`; an unsupported media type returns `415`. Removal is idempotent and remains available when delivery is disabled. The response contains only status, device ID, and provider. Provider tokens are never returned or logged; when enabled they are stored as versioned XChaCha20-Poly1305 ciphertext with endpoint/device/provider-bound associated data, and the outbox retains only endpoint IDs and delivery bookkeeping.

  Optional FCM HTTP v1 and direct APNs adapters are independently configured at server startup. FCM requires `ATERMIUS_FCM_SERVICE_ACCOUNT_FILE` to point to an absolute owner-only Google service-account JSON file; the server uses fixed HTTPS Google OAuth/FCM endpoints. APNs requires `ATERMIUS_APNS_PRIVATE_KEY_FILE` to point to an absolute owner-only P-256 `.p8` key plus `ATERMIUS_APNS_TEAM_ID`, `ATERMIUS_APNS_KEY_ID`, and `ATERMIUS_APNS_TOPIC`; the optional exact value `ATERMIUS_APNS_USE_SANDBOX=true` selects Apple's fixed sandbox endpoint, while the default is the fixed production endpoint. Each provider can be enabled without the other, and a server can enable both. A selected provider without valid configuration returns `503 PUSH_DELIVERY_DISABLED` and stores no token. FCM can carry the generic background data hint to FCM-registered Android or iOS apps; APNs sends only a silent background `content-available` hint. Existing WebSocket and polling sync are unchanged. With a provider configured, a successful Vault sync push inserts one coalesced durable `sync_available` hint for each other active member device inside the same SQLite transaction as record versions, heads, events, receipts, batch receipt, and audit event. Recipient eligibility is checked at enqueue time. Provider payloads contain only the generic `sync_available` hint; no Vault ID, record ID, Host, or envelope is sent. Provider I/O runs after the transaction under a 30-second lease and 10-second send timeout; retry delay starts at five seconds, doubles to a 15-minute cap, and dead-letters after eight attempts. Delivery is at-least-once, so lease recovery and retry can repeat this generic hint; clients should coalesce it and perform their ordinary authorized pull. A new commit or endpoint re-registration reawakens a dead-letter. An endpoint is deleted only when FCM returns HTTP 404 with an explicit `UNREGISTERED` error or APNs returns HTTP 410 with an explicit `Unregistered` reason; other provider failures remain retryable. A generic hint already queued at authorization time may still be sent after later membership revocation because the outbox intentionally does not retain Vault identity.

  Token encryption and keyed token fingerprints use separate HKDF-SHA256 domain-separated keys derived from the server's existing `auth-rate-limit.key`. That file also protects other server features and is not a push-only rotation key: preserve and restore it together with the SQLite database. If its key ID no longer matches a stored token envelope, decryption fails closed and delivery is parked; restore the matching database/key backup or re-register the endpoint. Any overall server-key rotation needs separate operational review.

  `GET /api/v1/notifications` upgrades to WebSocket only when its single `Origin` header exactly equals `ATERMIUS_PUBLIC_ORIGIN`; absent, duplicate, malformed, or different origins return `403 ORIGIN_DENIED`. Browser clients use the browser-supplied page origin. Native clients must send the origin (`scheme://authority`) of their configured API base URL, which must be exactly the configured public origin; if those origins differ, use polling. The server does not expose the configured origin through the instance endpoint and does not support a local-origin exception. After upgrade, the first frame must be a text JSON object within 10 seconds and 2048 bytes: `{"type":"authenticate","ticket":"<ticket>"}`. No bearer or refresh token is accepted in the URL or WebSocket frame. Authentication/replay/expiry failure sends `{"type":"error","code":"AUTH_REQUIRED"}` and closes with code `4001`. Malformed first frames use the same response. After authentication, application data frames from the client are rejected with close `1008` and `PROTOCOL_ERROR`.

  Success begins with exactly `{"type":"ready","server_generation":"<uuid>","sync_required":true,"heartbeat_seconds":30,"poll_interval_seconds":2}`. The client should immediately perform its normal pull/sync. Subsequent `sync_required` frames are exactly one of: `{"type":"sync_required","vault_id":"<uuid>","commit_seq":"<decimal string>"}` when that vault's record commit sequence advances; `{"type":"sync_required","vault_id":"<uuid>","conflict_seq":"<decimal string>"}` when its conflict creation/resolution sequence advances; or `{"type":"sync_required","vault_id":null,"commit_seq":null}` when membership, role, or vault availability changes. The record frame omits `conflict_seq`; the conflict frame omits `commit_seq`; the membership frame contains only the null `vault_id` and null `commit_seq` fields. Frames carry no record, object, or ciphertext data; normal authorized pull APIs remain authoritative. Membership and session/device/account state are rechecked every two seconds. A server WebSocket Ping is sent every 30 seconds and clients must automatically answer with Pong; no application heartbeat frame is used. Every outbound WebSocket write has a one-second deadline; a timed-out or failed write drops that socket and its connection permits so a slow consumer cannot indefinitely hold server capacity or suspend authorization polling. Under query pressure an individual poll may be skipped and retried on the next interval.

  The server permits at most 256 connections instance-wide, 8 per user, 4 per session, and 32 simultaneous poll queries; subscriptions are limited to 4096 vaults per connection. HTTP capacity rejection before upgrade returns `503 NOTIFICATIONS_BUSY`. A per-user/session connection cap sends `{"type":"error","code":"NOTIFICATIONS_BUSY"}` and close `4008`; a subscription-limit policy violation sends `NOTIFICATIONS_LIMIT` and close `1008`. Transient server/query capacity failures send `INTERNAL` or `NOTIFICATIONS_BUSY` and close `1011`; clients may retry with full-jitter backoff from 1 to 30 seconds and obtain a fresh ticket for every reconnect. Client normal close `1000` should not reconnect automatically; `4001` requires refreshing authentication and a new ticket; `4008` should retry only after a connection slot may have freed; `1008` requires correcting the client/configuration or falling back to polling. Notifications are best-effort hints, never a substitute for polling or cursor recovery.
- SSH Relay is disabled by default. Enabling it requires `ATERMIUS_RELAY_ENABLED=true`, a non-empty `ATERMIUS_RELAY_ALLOW_CIDRS` list, a non-empty exact-port `ATERMIUS_RELAY_ALLOW_PORTS` list, and a configured `ATERMIUS_PUBLIC_ORIGIN`. Ports are integers from 1 through 65535; malformed or over-limit CIDR/port lists fail closed and leave Relay disabled. Deployment policy accepts at most 256 CIDRs (each at most 64 bytes) and 4,096 ports. `POST /api/v1/relay/tickets` accepts `{device_id,target_host,target_port}` and returns HTTP 200 `{ticket,expires_at,connect_path}`. `target_host` accepts an IP literal or a DNS hostname in ASCII IDNA A-label form, at most 253 normalized bytes (a single trailing root dot may make the request value 254 bytes); labels are 1–63 ASCII characters, ASCII letters are normalized to lowercase, and one final dot is removed. IP literals skip DNS. A hostname is resolved once for A and AAAA with a two-second timeout and at most 32 total candidates. At most 32 DNS resolutions run concurrently without queueing; saturated resolver capacity returns `503 RELAY_BUSY`. The server inspects every answer and chooses the first address permitted by the effective CIDR policy and exact port policy while still denying loopback, unspecified, link-local, multicast, broadcast, IPv4-mapped forbidden addresses, and known cloud metadata addresses (including Alibaba Cloud's `100.100.100.200`) even when a CIDR includes them. The selected IP, not the hostname, is encrypted into the one-use ticket; the relay socket dials that pinned IP and performs no second resolution. A malformed hostname or zero port returns `400 INVALID_TARGET`; valid syntax with no DNS answers, resolver failure/timeout, or over-limit answers returns `502 TARGET_RESOLUTION_FAILED` without echoing the hostname; a resolved set with no allowed candidate or a disallowed IP/port returns `403 TARGET_DENIED`.

  Tickets are random canonical 32-byte base64url-no-pad values. They are stored as a SHA-256 hash, expire within 30 seconds (or at the session's exact access expiry if sooner), and are bound to the issuing active account, device, and session. Logout, refresh, device revocation, account deletion, expiry, and replay prevent dialing. Within 10 seconds after upgrade, the first text or binary WebSocket frame at `GET /relay/v1/connect` must be the raw ticket string/bytes, not JSON; a valid ticket is atomically consumed once and its target address is cleared from the ticket row. The WebSocket handshake requires exactly one `Origin` header equal to `ATERMIUS_PUBLIC_ORIGIN`; missing, duplicate, malformed, or different origins return `403 ORIGIN_DENIED` before upgrade. The server rechecks session/device/account state before forwarding and every two seconds during the connection. TCP and WebSocket write futures are supervised by those session checks and the absolute connection deadline; each pending write is bounded to 30 seconds, each session query to five seconds, and WebSocket/TCP close or half-close to two seconds. A failed or timed-out session check closes the relay.

  Issuance is serialized with session revocation and limited to 20 tickets per account per 60 seconds. The ticket table retains at most 100,000 recent rows; temporary ticket-store or bounded resolver-capacity exhaustion returns `503 RELAY_BUSY`. The server permits at most 256 active Relay connections instance-wide and four per user. Each connection is limited to one hour and 1 GiB transferred in both directions combined. Issue throttling returns `429 RELAY_RATE_LIMITED` with `Retry-After`; a missing/mismatched session returns `401 AUTH_REQUIRED`, an inactive device returns `403 DEVICE_REVOKED`, and disabled policy returns `503 RELAY_DISABLED`.

  Successful ticket issuance and TCP connection establishment create account-scope audit events `relay.ticket_issued` and `relay.connected` respectively, in the same transaction as issuance or the connection-liveness check. Audit data contains only actor IDs, fixed action/resource labels, result, source, and time; it never stores the target address, port, host name, ticket, SSH bytes, or payload. Ticket rows hold the destination only until consumption/cleanup and are never exposed by an API. This v1 relay target policy supports IP literals and validated DNS hostnames under the deployment, instance, and authenticated-account CIDR/port intersection. DNS is resolved once at ticket issuance, all bounded A/AAAA answers are checked, and the allowed selected IP is pinned through ticket consumption and TCP connect. Group-specific network rules remain unimplemented.
- Web terminal observer collaboration v1 is disabled by default. Enable it with `ATERMIUS_TERMINAL_COLLABORATION_ENABLED=true` and `ATERMIUS_PUBLIC_ORIGIN`. It is a single-process, memory-only encrypted frame router; the host owns SSH and terminal plaintext. `POST /api/v1/vaults/{vault_id}/terminal-sessions` requires an active host session/device and active Vault membership and accepts `{protocol_version:1,session_id,expires_at,observers:[{user_id,device_id,keybox}]}`. The canonical session UUID expires at a UTC RFC3339 time no more than 15 minutes ahead. There must be one to eight distinct active devices of active Vault members. A keybox has format `atermius-terminal-keybox-v1`, exact session/Vault/current membership_version, host and observer user/device IDs, role `observer`, epoch 1, matching expires_at, an 80-byte decoded base64url-no-pad crypto_box_seal ciphertext, and an Ed25519 signature. The host signs JCS of all keybox fields except signature; the server verifies it using the registered host device key and never opens the sealed bytes. The response is `{session_id,expires_at,host_ticket,connect_path:"/collaboration/v1/connect"}`.

  `POST /api/v1/vaults/{vault_id}/terminal-sessions/{session_id}/ticket` has no body and can issue a ticket only to the exact active member device named in the signed allowlist. It returns `{ticket,role:"observer",keybox,ticket_expires_at,connect_path}`. The ticket deadline is bounded by 30 seconds, the room expiry, and that login session's access expiry; it is distinct from the signed keybox/session expires_at. Ticket creation, consumption and room creation recheck account, device, login session, active Vault membership, membership version and explicit target under SQLite writer ordering. Tickets are random 32-byte base64url-no-pad values held only as SHA-256 hashes in process memory. They are one-use, bound to user/device/login session/server generation/room/role, and never appear in URLs or durable storage. `DELETE /api/v1/vaults/{vault_id}/terminal-sessions/{session_id}` stops only the original host device's room and returns `{status:"stopped"}`.

  `GET /collaboration/v1/connect` is outside `/api/v1` and requires exactly one Origin equal to `ATERMIUS_PUBLIC_ORIGIN`. The first text message within 10 seconds is `{"type":"authenticate","ticket":"..."}`. After successful ticket consumption the server sends `{"type":"authenticated","role":"host"|"observer","session_id":"..."}`. The host sends one signed recipient-bound frame per observer: format `atermius-terminal-frame-v1`, session/Vault/membership and host/recipient IDs, role `observer`, epoch 1, positive sequence, kind `output` or `resize`, canonical 24-byte nonce, authenticated XChaCha20-Poly1305 ciphertext+tag, and Ed25519 signature over JCS of every frame field except signature. Sequence numbers may start at any positive value for an observer with no history, then must be the exact next value per observer and kind; the maximum is 9007199254740991. The server retains no output history. It may retain only each approved target’s latest signed opaque resize frame and queues that frame after authentication but before later live frames, so a late observer can set the terminal dimensions. The host chunks plaintext output to at most 16 KiB; observers cannot send application data, input, or resize commands. The server validates signed context and encoded size without decrypting frames. Limits are 64 KiB per JSON message, eight observers, 256 frames and 4 MiB of ciphertext per room per second, 256 MiB total encoded ciphertext-field bytes per room, and 32 queued frames per observer. Slow observers are disconnected. Account/device/session and active Vault membership/version are writer-rechecked every two seconds and before every host frame. Host disconnect/stop, expiry, Vault membership-version change, Vault deletion, or server restart closes/removes the room; rejoin requires a new key and session. Keyboxes, tickets, frames and terminal history are not written to SQLite or audit logs. Native transports, input-controller election, replay history, reconnect/resume and multi-server room fanout are not in v1. See `protocol/TERMINAL-COLLABORATION.md` for the complete cryptographic context.
- `GET /health/live` and `/health/ready` return minimal health state and no account information.

## Account deletion

POST /api/v1/account/delete requires the current bearer session and a JSON body containing login_verifier, a base64url-no-pad 32-byte verifier derived by the client. The master password is never sent. The proof consumes the existing login-rate-limit bucket before Argon2 verification. Success returns status, requested_at, purge_after and can_cancel. The default grace is seven days; ATERMIUS_ACCOUNT_DELETION_GRACE_SECONDS accepts 60 through 7776000 seconds (90 days). If the account owns a vault with another active or invited member, deletion is blocked with 409 ACCOUNT_OWNS_SHARED_VAULT; ownership is never transferred and another account's shared data is never deleted.

Deletion immediately marks the account deleting and revokes every active device and session in one SQLite writer transaction. Authentication stops immediately. If the successful DELETE response is lost, the revoked bearer is not restored and cannot be used to retry or query status; no second pending audit row is created. The user can safely use the sessionless cancellation flow below with username plus login_verifier, which restores the account and only devices revoked by this deletion request, but never restores sessions. The user must then log in again. `POST /api/v1/auth/prelogin` returns the stored KDF parameters for both active and deleting accounts so the client can derive the verifier needed for cancellation; it does not return the account state. `POST /api/v1/auth/login` remains unavailable while deleting and returns the same `AUTH_REQUIRED` response as for an unknown username or wrong verifier. Cancellation uses the normalized-username and peer login limiter and Argon2 verifier; unknown usernames and invalid proofs return the same 401 REAUTH_REQUIRED. Repeating cancellation after the account is already active is an idempotent success. At or after the deadline, before maintenance purges the account, cancellation returns 410 ACCOUNT_DELETION_WINDOW_EXPIRED. A separate account-deletion status endpoint is not part of this contract.

When the deadline expires, maintenance atomically deletes personal vaults, credentials, devices, sessions, account snapshots, invitations, uploads and the user's shared-vault membership/key envelopes. Other accounts' shared vaults and ciphertext history remain available. Immutable shared revisions may contain signatures by the deleted account's devices, so maintenance preserves only referenced public signing/encryption keys in a vault-scoped archive. It contains opaque user/device IDs and public keys, but no device name, username, token, credential, private key or ciphertext. Only a current member of that vault can read the archive directory. The audit row keeps a domain-separated HMAC actor hash and lifecycle timestamps; its account ID is cleared on cancellation or purge, and terminal rows use the shared ATERMIUS_AUDIT_RETENTION_DAYS policy. Pending audit rows are never pruned.

## Audit events

`GET /api/v1/audit?cursor=<opaque>&limit=100` returns committed control-plane metadata visible to the caller. The default page size is 100; `limit` must be in `[1,200]`, otherwise `400 INVALID_LIMIT`. Response shape:

```json
{
  "events": [{
    "event_id": "123",
    "scope": "vault",
    "vault_id": "vault-uuid",
    "actor_user_id": "account-uuid",
    "actor_device_id": "device-uuid",
    "action": "vault.key_rotated",
    "resource_type": "vault",
    "resource_id": "vault-uuid",
    "result": "success",
    "occurred_at": "2026-09-27T12:00:00Z",
    "source": "api"
  }],
  "next_cursor": "<opaque-or-null>",
  "has_more": false
}
```

Account-scope events are visible only to that authenticated account. Vault-scope events are visible only to users with a current active `owner` or `editor` membership in that vault; viewers and nonmembers receive no such rows. Authorization is recomputed on every page. Vault-scope reads remain available to active Owner/Editor members during vault deletion grace, and disappear after the vault is purged. A cursor is HMAC-authenticated and bound to the requester, server generation, fixed global event high-water mark and last event ID. A cursor from another account or with modified fields returns `400 INVALID_AUDIT_CURSOR`; a cursor from a prior server generation returns `410 AUDIT_CURSOR_EXPIRED`. New events after the first page are excluded from the current traversal.

A sync push that commits at least one new operation writes exactly one `vault.sync_batch_committed` Vault-scope event in the same transaction. The event records the authenticated user/device actor, `resource_type: "sync_batch"`, `resource_id: null`, success result and API source. It has no record/op/revision identifier, operation type or count, ciphertext, or request payload. Empty, failed, and fully idempotent pushes add no event; a mixed batch adds one only if at least one operation is newly committed. If the audit insert fails, the push transaction rolls back.

The server records successful committed changes for account creation/deletion/cancellation, password change, device registration/revocation, recovery configuration/envelope changes (`auth.account_recovery_enabled`, `auth.account_recovery_rotated`, `auth.account_recovery_disabled`, `auth.account_recovery_key_envelopes_updated`), recovery completion (`auth.account_recovered`), TOTP MFA challenge/enrollment/recovery-code rotation/disable (`auth.mfa_login_challenge_created`, `auth.mfa_totp_enabled`, `auth.mfa_recovery_codes_rotated`, `auth.mfa_totp_disabled`) and full-Recovery reset (`auth.mfa_reset_by_recovery`) and restore-state invalidation (`auth.mfa_state_reset_by_restore`), vault creation, invitation creation/acceptance, membership changes, key rotation, committed sync push batches, vault conflict resolution, and vault deletion/cancellation/purge. Password-change success is `auth.password_changed`; an attributable rejected current verifier emits `auth.password_change_failed` on a best-effort basis. Both are account-scope events with the authenticated user/device actors and the account as resource. Successful Relay ticket issuance and TCP connection establishment emit `relay.ticket_issued` and `relay.connected`, respectively, as account-scope events with authenticated user/device actors and `resource_type: "relay"`; they contain no target address, port, ticket or SSH data. The first successful `POST /api/v1/vaults/{id}/conflicts/{cid}/resolve` writes one Vault-scope `vault.conflict_resolved` success event in the same transaction, with the authenticated actor and `resource_type: "conflict"` / `resource_id: {cid}`. It records no record ID, revision ID, envelope, or payload. An idempotent same-revision retry, stale/unauthorized request, or failed resolution writes no event; audit insertion failure rolls back the conflict resolution. Recovery changes use account scope, result `success`, the authenticated account/device as actors, and `resource_type: "account_recovery"` with the account ID as `resource_id`; recovery completion uses `resource_type: "account"`. These writes are in the same transaction as the recovery state/receipt changes. They contain no recovery code, credential, key envelope, host data or request body. A successful authenticated logout emits `auth.logout_succeeded` in the same transaction that revokes its session, with `resource_type: "session"` and only the opaque session ID in `resource_id`; it does not store the session token, refresh token, username, or request details. Unauthenticated, expired, or otherwise invalid logout attempts are not recorded. If the audit insert fails, the session revocation rolls back with the transaction. Reuse of a previously consumed refresh token emits one `auth.refresh_reuse_detected` failure event only when that replay revokes an active session family. The event is account scoped, has null actor IDs, `resource_type: "session_family"`, and only the random family UUID in `resource_id`; it stores no token, account/device ID, IP address, User-Agent, or request details. Its insert is best effort so an audit storage error cannot prevent family revocation or change the replay's `401 AUTH_REQUIRED` response. Further replays after revocation do not create duplicate events; unknown refresh tokens with no matching history are not audited. A signed key rotation emits one `vault.member_role_changed` event for each member whose role changes and one `vault.member_revoked` event for each member whose ACL state becomes revoked; if the role and state both change for one member, the revocation event represents that change. These Vault-scope events use `resource_type: "membership"` and put only the target's opaque user ID in `resource_id`; they do not store a username, email or arbitrary details. Each remains in the same transaction as the signed membership/key rotation. `vault.key_rotated` and, when applicable, `vault.ownership_transferred` remain separate events. `event_id` is a decimal string. `scope` is `account` or `vault`; `vault_id` is null for account scope. Account scope IDs are stored as a domain-separated HMAC of the account ID under an instance secret and are not returned. Actor and resource IDs are opaque identifiers; actor fields and account, account-recovery, device, membership, session, and session-family resource IDs become null when that account is permanently purged. Account deletion grace/cancellation does not anonymize events. Events are retained for `ATERMIUS_AUDIT_RETENTION_DAYS` (default 365, range 1..3650), then removed by maintenance.

Audit rows contain only scope, opaque actor/resource identifiers, fixed action/result labels, UTC time and the source enum `api` or `maintenance`. They never contain source IP, User-Agent, host names, terminal commands, usernames/emails, login verifiers, credentials, invitation tokens, session tokens, request bodies, ciphertext, secret envelopes or arbitrary detail JSON. Successful login is recorded as `auth.login_succeeded` with result `success` in the same transaction that creates its session. A failed verifier for a known active account, or a correct verifier presented by an inactive device, is recorded as `auth.login_failed` with result `failure`, account-HMAC scope, null actor IDs and null resource ID; the unverified device ID is not stored. Audit write failure for this event does not change the authentication response. Unknown usernames and non-active accounts are not recorded because they cannot be safely attributed to an account; they continue through the dummy Argon2 path and return the same 401 `AUTH_REQUIRED` envelope as a wrong verifier. Rate-limited attempts and prelogin requests are not audited. Successful and attributable failed login events are visible only through that account's normal audit scope. These rows are authentication outcomes, not a source-address or request-access log.

### Embedded remote desktop gateway (2026-11-06)

`GET /desktop/v1/connect` upgrades to a binary WebSocket when Relay is enabled and `ATERMIUS_GUACD_ADDRESS` is configured. It consumes the same one-use ticket issued by `POST /api/v1/relay/tickets`; the ticket's IP/port is the RDP/VNC target, not guacd. Browser `Origin` must exactly match the configured public origin. Native clients may omit Origin, but still require a valid ticket. The first frame is the raw ticket; the next text frame is JSON with `protocol` (`rdp`/`vnc`), optional `username`, `password`, `certificate_sha256` (RDP only, 64 hex digits), and optional `width`/`height` (320–4096 / 200–4096, defaults 1280×800). Unknown fields are rejected.

The server performs the Guacamole handshake using only the ticket's pinned destination, then forwards binary UTF-8 Guacamole instructions. Client frames must contain complete instructions; only keyboard, mouse, size, sync, ack, bounded text clipboard/blob/end, nop and disconnect operations are accepted. Client select/connect/argv/file/pipe instructions are rejected. Existing Relay user/global limits, traffic/duration limits, account/device/session checks, PostgreSQL leases and revocation polling apply. Passwords are not placed in URLs, ticket persistence or audit metadata. guacd sees session credentials and desktop contents; it is a trusted gateway. See `docs/REMOTE-DESKTOP.md` for deployment and platform boundaries.
