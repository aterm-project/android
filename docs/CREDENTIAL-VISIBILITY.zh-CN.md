# 凭据可见性：私密加密与管理员可见

[English](CREDENTIAL-VISIBILITY.md) · [API 契约](../protocol/API-CONTRACT.md#credential-visibility-v1) · [文档导航](README.md)

多用户服务器上的每个账户都有一个**凭据可见性模式**，只能由实例管理员设置。用户不能自行更改，客户端始终会明确显示当前模式。

| 模式 | 管理员能看到什么 | 用户看到什么 |
| --- | --- | --- |
| `private` 私密加密（默认） | 看不到任何已保存的主机凭据，即原有的零知识行为。忘记主密码时，管理员也无法帮助恢复这些数据。 | 账户设置中的绿色“私密加密”说明。 |
| `admin_visible` 管理员可见 | 该账户所在保险库中的全部内容：主机名称和地址、用户名、密码、私钥、口令及其他保存项。 | 琥珀色“管理员可以查看你的凭据”提示、常驻标识、模式变更时的一次性确认，以及最近的管理员查看记录。 |

**两种模式下主密码都不会发送到服务器**，任何管理员都看不到主密码。`admin_visible` 不允许管理员以该用户身份登录，也不会托管账户密钥。

本文说明服务端契约与信任模型；用户提示、自动托管上传和管理员查看器由各客户端实现。

适用范围：仅 SQLite 部署。在受限 PostgreSQL sync-core 运行时中，这些路由不会注册，不会声明 `credential_visibility` 能力，`/me` 返回 `credential_visibility: null`。

## 工作方式

1. **托管密钥。** 管理员客户端生成 X25519 密钥对和 20 字节恢复码。上传到服务器的只有：公钥、设备签名的创建声明、用该管理员账户密钥包裹的私钥，以及用恢复码经 Argon2id 派生的密钥包裹的私钥。服务器用实例密钥对公钥描述签名；客户端使用前会用已固定的实例公钥校验该签名。
2. **托管上传。** `admin_visible` 账户的客户端在登录、解锁、新建保险库、轮换密钥或接受共享后，把自己持有的每个保险库密钥用 `crypto_box_seal` 封装给托管公钥，用设备密钥签名后上传。服务器只保存密文。
3. **查看。** 管理员需重新输入自己的主密码。其客户端派生账户密钥，在内存中解开托管私钥，校验并打开托管内容，再解密该账户的保险库记录。查看器只读，关闭后丢弃密钥。其他管理员可用恢复码打开托管密钥，然后保存自己的包裹。
4. **记录。** 通过 API 每读取一页记录，都会在同一事务中写入一条实例审计事件（不合并）。这次读取还会写入**该保险库每一位活跃成员**的查看记录，而不只是管理员指定的那个账户，因为共享保险库里也有其他成员的条目。本页记录的每位作者也会收到查看记录，即使其成员关系此时已被组织以 `none` 限制隐藏或已被撤销（隐藏可以撤回，而这次读取确实暴露了该账户保存的内容）。每条记录按同一管理员、账户和保险库在 10 分钟内合并；每个账户保留最近 200 条。每个受影响的账户都会看到“管理员 X 于 T 查看了你的凭据”，并收到一条账户审计事件。列出某账户的托管内容不算查看任何人的凭据，但只要列表返回了至少一条托管内容，就会写入一条实例审计事件（`instance.credential_escrow_listed`）。

服务器和数据库从不持有能打开托管内容、包裹或记录的密钥。即使拿到数据库导出和服务器上的全部密钥文件，**只要猜不中某位管理员的主密码或恢复码**，也无法解密这里的任何内容：数据库中保存着每位管理员的 KDF 盐、登录校验值和账户密钥信封，旁边就是该管理员的托管密钥包裹（见“信任模型与限制”）。恢复码有 160 位熵，存储的恢复包裹无法被离线猜解；主密码则有可能被猜中。

## 信任模型与限制

启用 `admin_visible` 前请阅读：

* **依赖用户客户端。** 托管内容由用户自己的设备上传。被修改或过旧的客户端可以不上传，或上传无效的密钥；管理员会看到 `pending`（待托管），或在查看器中看到解密失败。服务器无法强制或核验托管明文。
* **切换为私密无法撤销已发生的查看。** 账户切换为 `private` 后，会立即删除其保险库在服务器上的托管内容（若共享保险库中仍有其他处于 `admin_visible` 的活跃成员则保留，见下文），并阻止后续查看。但已经被管理员查看、复制或记录下来的内容无法收回。**切换为私密后，请更换重要的密码和密钥。** 客户端在模式切换为私密时会显示这一建议。
* **共享保险库。** 只要保险库中有任一活跃成员处于 `admin_visible`，管理员就能读取整个保险库，包括其他成员添加的条目。保险库列表会显示“管理员可见”标记，共享流程会提示成员。所有者邀请他人或向组织授权成员分发保险库密钥之前，客户端会先向服务器确认对方账户是否处于 `admin_visible`，如果是，必须明确确认才能继续，因为共享后保险库中的全部内容（包括所有者自己保存的密码）都会对管理员可见。所有者因此会得知对方的模式；即使不问，对方加入后保险库标记也会显示这一点。属于这类保险库的 `private` 账户会得到说明：私密模式提示会写明这一例外，账户设置也不会声称管理员什么都看不到。每位活跃成员（包括 `private` 成员）以及被读取记录的每位作者，都会在自己的查看记录中看到对该保险库的每次读取。管理员之后仍可把现有成员改为 `admin_visible`，此时其他成员只能从保险库标记得知。
* **最弱的管理员主密码保护着所有 `admin_visible` 账户。** 每位管理员的账户密钥都能打开该管理员的托管密钥包裹，进而打开全部托管内容。拿到数据库的人（明文文件、加密文件加上其密钥文件，或备份加上备份密钥）可以利用存储的 KDF 盐和校验值离线猜解任意一位管理员的主密码；只要猜中一个，就能打开所有 `admin_visible` 账户的保险库。服务器不强制管理员的密码强度或 KDF 参数。请要求管理员使用足够长的随机主密码，尽量减少管理员人数，启用数据库加密（见下文“静态数据：数据库加密”），并把数据库密钥、备份密钥和数据卷分开保管。
* **没有管理员可见成员，就没有托管内容。** 只有在保险库中至少有一位活跃成员处于 `admin_visible` 时，托管内容才会保留。最后一位这样的成员离开时（切换为私密、被所有者通过密钥轮换或所有权转移移除、被组织限制为 `none`，或账户被清除），服务器会在同一事务中删除该保险库的托管内容。之后即使把剩余成员改为 `admin_visible`，也要等该成员自己的客户端重新托管后，管理员才能读取该保险库。
* **同时运维服务器的管理员。** 查看记录覆盖的是通过 API 的读取。同时掌握托管私钥和数据库直接访问权限的人（例如兼任管理员的服务器运维者）可以离线解密托管内容和记录，而不产生查看记录。数据库静态加密能保护被盗的数据库文件和备份，但不能防范运维者本人（见下文“静态数据：数据库加密”）。
* **离任管理员。** 从 `ATERMIUS_ADMIN_USERNAMES` 移除用户名会立即阻止其使用管理 API，但无法删除其可能保存的托管密钥副本。若需让离任管理员失去访问能力，请重置托管密钥；客户端随后会用新密钥重新托管。
* **密钥丢失。** 如果所有管理员包裹和恢复码都丢失，任何内容都无法解密。请重置密钥：`admin_visible` 账户在新密钥建立前显示 `no_key`，在客户端重新托管前显示 `pending`。
* **已停用账户。** 已停用的 `admin_visible` 账户在其保险库成员关系仍有效时依然可被查看。这是有意设计，便于组织在人员离开后取回凭据。账户停用期间其客户端无法新增托管。通过已停用（或删除中）的账户读取时，该保险库的每位活跃成员仍会看到这次读取；已停用账户本身只有在重新启用后才能看到，被删除账户的查看记录会在账户清除时一并删除。
* **已清除账户。** 账户被清除后，其设备公钥会保留在保险库的设备归档中，因此它在共享保险库中留下的托管内容和记录仍可由管理员客户端校验。其自身账户审计记录中的保险库 ID 会被清空。
* **成员之间的干扰。** 托管内容不会被覆盖。共享保险库中恶意的 `admin_visible` 成员可以抢先上传无效密钥。这只影响管理员对该保险库的可见性，而该成员本来也可以选择不上传。重置密钥会清除全部托管内容。

## 管理

* **实例默认值。** 新账户采用实例默认模式（新服务器为 `private`），除非邀请中指定了模式；首个（bootstrap）账户也使用默认值。修改默认值不会改变已有账户。默认值为 `admin_visible` 时，注册页面会在创建账户前显示管理员可见提示（`/api/v1/instance` 返回 `credential_visibility_default`）。
* **单个账户。** `PUT /api/v1/admin/accounts/{user_id}/credential-visibility`，请求体 `{"mode":"private"|"admin_visible"}`。管理员可以修改自己的账户。本功能安装时，已有账户均为 `private`。
* **单个邀请。** `POST /api/v1/admin/account-invitations` 接受 `credential_visibility`；运维命令行也支持相同选项：

  ```sh
  docker compose --env-file deploy/.env -f deploy/compose.yaml exec -T server \
    /usr/local/bin/atermius-server create-account-invite \
    --username 'person@example.com' --credential-visibility admin_visible
  ```

* **托管密钥。** 在管理员客户端中创建一次。恢复码只显示一次，请离线保存。其他管理员用恢复码打开托管密钥。重置（`DELETE /api/v1/admin/credential-escrow/key`，请求体 `{"key_id":…,"confirm":"reset"}`）会删除密钥、所有管理员包裹和全部托管内容。
* **状态。** `GET /api/v1/admin/accounts` 显示每个账户的模式和 `escrow_status`：`not_required`（无需托管）、`no_key`（尚无托管密钥）、`pending`（待托管）或 `complete`（已完成）。

### 审计事件

| 事件 | 范围 | 触发时机 |
| --- | --- | --- |
| `instance.credential_policy_changed` | 实例 | 实例默认模式变更 |
| `instance.credential_visibility_changed` | 实例 | 账户模式变更（账户 ID 经 HMAC 处理） |
| `account.credential_visibility_changed` | 受影响账户 | 同一变更，用户可见；操作者为管理员账户 |
| `instance.credential_escrow_key_created` | 实例 | 注册托管密钥 |
| `instance.credential_escrow_key_wrap_stored` | 实例 | 管理员保存或替换自己的包裹 |
| `instance.credential_escrow_key_reset` | 实例 | 删除密钥、包裹和托管内容 |
| `instance.credential_escrow_listed` | 实例 | 管理员列出某账户的保险库，且列表返回了至少一条托管内容（账户 ID 经 HMAC 处理） |
| `instance.credential_escrow_viewed` | 实例 | 管理员每读取一页记录（被指定账户的 ID 经 HMAC 处理） |
| `account.credential_viewed_by_admin` | 保险库的每位活跃成员，以及被读取记录的每位作者 | 同一读取，每个受影响账户可见；资源为保险库 ID；按同一管理员、账户和保险库在 10 分钟内合并 |

事件不包含任何密钥、包裹、托管内容、信封或记录内容。

### 运维说明

* 记录读取限额（每位管理员每分钟 120 页）保存在进程内存中，按服务器进程计算，重启后清零。
* 备份会像其他表一样包含托管相关的表。托管内容和包裹是密文，没有管理员账户密钥或恢复码无法打开；账户模式、实例默认值和查看记录则是普通数据行，静态存储时只能靠数据库加密保护（见下文“静态数据：数据库加密”）。恢复旧备份后，如果该备份之后曾轮换或重置托管密钥，请考虑再次重置。
* 实例签名密钥轮换后，服务器会用新密钥重新签名已存储的描述，前提是它原本由已验证轮换链中的某个密钥签名。客户端继续用已固定的实例公钥校验。
* 跨实现测试向量：`protocol/test-vectors/credential-escrow-v1.json`。

## 静态数据：数据库加密

托管状态保存在主 SQLite 数据库的普通表中：`instance_credential_policy`、`credential_escrow_keys`、`credential_escrow_key_wraps`、`credential_escrow_envelopes`、`credential_admin_views`，以及 `users` 和 `account_invitations` 表中的 `credential_visibility` 列。启用[数据库静态加密](runbooks/database-encryption.md)（`ATERMIUS_DATABASE_KEY_FILE`）后，SQLCipher 会把这些表与其他数据一起加密，覆盖 `atermius.db`、其 WAL、备份快照和恢复暂存。托管数据没有单独的开关。管理员可在 `GET /api/v1/admin/overview` 的 `database_encryption` 字段确认是否已启用；客户端的实例概览和凭据可见性管理会在该值为 `disabled`（数据库未静态加密）时显示警告，为 `enabled` 时显示简洁的“已静态加密”状态。

SQLCipher 为托管数据带来的保护：

* **被盗文件无法用于离线攻击。** 托管内容和包裹本身就是服务器无法打开的密文。明文数据库的薄弱点在它们旁边：管理员的 KDF 盐、登录校验值和账户密钥信封，与该管理员的托管密钥包裹存放在同一个文件里。拿到明文数据库文件的人可以离线猜解该管理员的主密码，一旦猜中，就能解开托管密钥并打开全部托管内容。数据库加密后，没有密钥文件时，被复制的数据库文件、WAL、备份快照或卷副本都无从猜解。
* **隐藏元数据。** 明文数据行会暴露哪些账户处于 `admin_visible`、哪些保险库有托管内容、实例默认值、查看记录（哪位管理员在什么时候查看了哪个账户的凭据）以及用户名。SQLCipher 让被盗文件中的这些信息全部不可读。
* **备份保持加密且内容完整。** 已加密实例的备份快照保持加密。备份和恢复（包括重新设置数据库密钥的恢复，以及把旧的明文归档加密后恢复）都会原样保留托管密钥、包裹、托管内容、查看记录和账户模式。

SQLCipher 不能防范的情况：

* **运行中的服务器。** 服务器运行期间，数据库密钥在进程内存中，SQLite 也在内存中读取解密后的数据页。拥有主机 root 权限、能转储内存或附加调试器的人，看到的数据与未加密时相同。
* **同时拿到密钥和数据库的人。** 同时持有密钥文件和数据库文件的运维者或攻击者，可以像打开明文数据库一样打开它。加密备份归档加上 `ATERMIUS_BACKUP_KEY_FILE` 也是如此，因为归档的加密载荷里带有数据库密钥。他们能读取上述元数据，并离线猜解管理员的主密码。托管内容仍然封装给托管公钥，打开它们需要管理员账户密钥或恢复码，而**猜中任意一位管理员的主密码就能得到其账户密钥**，所以最弱的管理员密码守护着全部托管内容。请把数据库密钥、备份密钥和数据卷分开保管，并要求管理员使用强主密码。
* **通过 API 的读取。** 静态加密对服务器透明。管理员通过 API 的读取由查看记录追踪，与加密无关。
* **之前留下的明文副本。** 启用加密前创建的备份，以及在 `database-encrypt` 之前存放过明文文件的存储介质，仍可能含有明文数据行，详见运行手册。

## 不在范围内

* PostgreSQL sync-core 部署（关闭，见上文）。
* 发生查看时向用户推送通知。查看会在客户端下次刷新时显示在账户设置和用户审计记录中。
* 托管保险库以外的内容，例如仅本地配置、从未保存到保险库的设备本地 SSH 密钥，以及主密码。
